# 子智能体分派 Rule

## 目标

把“主智能体协调、子智能体执行、执行后验收”的协作方式固化为可复用的分派协议，避免模糊分派、边界失控或未验收即收口。

## 适用场景

- 任务需要拆解给子智能体执行
- 任务需要先取上下文，再落实现或验证
- 任务完成与否依赖执行后验收
- 任务需要区分执行器与评估器边界

## 创建参数要求

每次调用 `spawn_agent` 创建子智能体时，必须显式给出创建参数，不要依赖默认值或隐式继承。至少要明确以下字段：

1. `agent_type`：明确当前子智能体是 `worker`、`explorer` 还是例外情况下的 `default`
2. `model`：明确本次使用的子模型
3. `reasoning_effort`：明确推理强度，如 `low`、`medium`、`high`、`xhigh`
4. `fork_context`：明确是否继承当前线程上下文，写成 `true` 或 `false`

推荐映射如下：

- 执行器子智能体：默认使用 `worker`
- 评估器子智能体：默认使用 `explorer`
- 只读取上下文、定位代码、梳理影响面或做验收判断时：优先使用 `explorer`
- 只有在任务性质无法明确归入 `worker` 或 `explorer` 时，才使用 `default`，并说明原因

补充要求：

- `reasoning_effort` 必须根据任务复杂度显式选择，不以“未填写则沿用默认值”代替判断
- `fork_context` 必须按最小必要上下文原则选择；只有确实需要完整继承当前线程上下文时才设为 `true`
- 若目标是尽量保持只读，应同时使用 `explorer`，并在任务文本里显式写明“禁止修改文件、禁止执行会写入状态的命令或操作”
- `worker` / `explorer` 只是推荐的角色映射，不是底层权限隔离；不得把 `explorer` 表述为平台已提供的硬性只读权限
- 上述只读要求属于角色和任务边界约束，不是底层权限沙箱；它依赖分派文本约束和后续执行纪律，而不是平台自动接管权限

## 分派模板

每次向子智能体分派任务时，至少要明确以下内容：

1. 任务目标：本次要达成什么结果
2. 当前角色：明确对方现在是执行器子智能体还是评估器子智能体
3. 创建参数：本次创建时显式使用的 `agent_type`、`model`、`reasoning_effort`、`fork_context`
4. 上下文范围：允许读取哪些文件、目录、规则或环境信息
5. 修改边界：允许修改哪些文件或模块
6. 禁止事项：哪些文件、模块、操作或扩展性动作不允许触碰
7. 预期产出：需要返回什么内容，如代码修改、验证结果、风险说明或建议
8. 验证标准：如何判断本次执行是否达标

子智能体在接收分派后，应先确认自己当前被分配的角色，再围绕上述内容执行，不需要也不应重新定义任务目标、补充新的主线流程或替主智能体决定是否要扩大范围。
子智能体的回复格式也应匹配当前角色，执行器侧重实现与反馈，评估器侧重检查与结论，不得以主智能体口吻做收口或调度。

## 边界模板

若任务允许修改文件，建议显式说明：

- 只允许修改的文件或目录
- 不得顺手修复与当前目标无关的问题
- 不得扩大为跨项目、跨模块重构
- 不得回退或覆盖非本次任务引入的已有改动
- 不得把发现的新问题直接升级为新任务主线；只能如实报告，由主智能体决定是否再分派
- 不得在角色不明确时自行假设为主智能体并开始统筹流程
- 若发现边界冲突或上下文不足，应先反馈，不自行扩张任务范围

## 验收模板

每次执行完成后，验收方至少检查以下内容：

1. 目标是否达成
2. 是否遵守了读取与修改边界
3. 是否遗漏明显风险、回归或未说明前提
4. 验证动作是否充分，结论是否可复查
5. 最终结论应明确表达为“通过 / 不通过 / 有风险待修复”

## 禁止事项

- 模糊分派，只给出笼统目标，不写边界与产出要求
- 创建子智能体时省略 `agent_type`、`model`、`reasoning_effort` 或 `fork_context`，把关键行为交给默认值决定
- 在未定义允许修改范围时直接让子智能体落地改动
- 执行完成后直接收口，不做验收
- 将“执行者自己验收自己”作为默认模式
- 未经过验收就对外宣称任务已完成

## 例外条件

- 若任务足够简单、低风险且边界清晰，主智能体可亲自执行简单动作
- 若任务足够简单、低风险且验证路径直接，执行者可在说明原因后自行验收
- 采用例外条件时，必须明确说明为何不需要独立执行器或独立评估器
- 一旦任务出现跨文件扩散、风险不明、验证不充分或结论不稳，应立即回到标准的“分派执行 + 独立验收”模式
- 子智能体不得以例外条件为借口接管主智能体的规划、收口或调度职责
