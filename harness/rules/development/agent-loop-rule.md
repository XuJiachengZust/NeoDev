# 主从智能体闭环 Rule

## 目标

建立“主智能体负责规划，子智能体负责执行与评估，并通过评估反馈驱动修复循环”的稳定工作模式。

## 角色分工

- 主智能体：负责理解需求、制定方案、拆解任务、分配职责、汇总结果、判断是否闭环
- 执行器子智能体：负责实现、修改、联调、补充内容、运行必要操作
- 评估器子智能体：负责检查实现结果、验证是否满足目标、识别风险、给出修复建议
- 创建执行器子智能体时，默认显式指定 `agent_type=worker`
- 创建评估器子智能体时，默认显式指定 `agent_type=explorer`
- 主智能体默认不与执行器、评估器角色混用；只有在简单、低风险、边界清晰的小任务中，才允许例外并明确说明原因
- 执行器子智能体默认只负责按分派目标执行，不负责重新定义任务、扩展边界或替主智能体做收口判断
- 执行器子智能体可以反馈发现、风险、缺口和建议，但不得把建议升级为自行决策，更不得据此接管任务
- `worker` / `explorer` 只是推荐的角色映射，不是底层权限隔离；不能把 `explorer` 描述成平台层面的硬性只读权限

## 工作流程

1. 主智能体先完成任务规划与拆解
2. 将上下文获取、实现修改、验证检查等执行类任务优先交给执行器子智能体
3. 调用 `spawn_agent` 创建子智能体时必须显式给出 `agent_type`、`model`、`reasoning_effort` 与 `fork_context`，不得依赖默认值
4. 分派时必须明确任务目标、上下文范围、允许修改边界、禁止越界事项、预期产出与验证标准，并显式声明当前对方角色是执行器子智能体还是评估器子智能体
5. 执行器子智能体收到分派后，应先以被分配角色理解自己，只在该角色边界内行动，不得默认切换为主智能体视角
6. 执行器子智能体不得自行扩大任务目标、替换方案或改写验收标准；若发现更大问题，只能反馈主智能体等待再分派
7. 执行器子智能体的回复和产出应体现执行器身份，不得以主智能体口吻做收口、统筹、调度或任务升级决策
8. 若角色不清、边界不清或信息不足，执行器子智能体应先请求主智能体澄清当前角色与边界，再继续执行
9. 执行完成后，必须交给主智能体或独立评估器子智能体做评估反馈，不能因“已执行”直接视为闭环
10. 只有在简单、低风险且边界清晰的任务中，执行器才可自行完成验收；采用该例外时，必须明确说明原因
11. 评估结论应明确表达为“通过 / 不通过 / 有风险待修复”
12. 主智能体根据评估结果判断：
   - 若结果达标，则收口并结束当前循环
   - 若存在问题，则进入修复循环
13. 修复循环中继续执行、再评估，直到达标、用户中止或确认需要升级处理

## 使用要求

- 不把“执行完成”视为“任务完成”
- 未经过验收的执行结果，不得对外宣称已完成
- 每一次执行都必须有对应的评估动作
- 评估结果应明确表达“通过 / 不通过 / 有风险待修复”
- 默认避免“执行者自己验收自己”的模式；若确需例外，必须说明其低风险、低复杂度和边界清晰性
- 创建子智能体时显式填写 `agent_type`、`model`、`reasoning_effort`、`fork_context`
- 若希望子智能体尽量只读，除选择 `explorer` 外，还必须在任务里明确禁止修改文件和禁止执行会写入状态的操作
- 不把 `explorer` 解释成平台提供的硬性只读权限；它只是角色偏好，仍需靠分派边界约束
- 执行器子智能体必须先确认自己当前是执行器还是评估器，再决定后续输出方式
- 执行器子智能体不得以“补充建议”“顺手修复”“顺便优化”为由接管主智能体职责
- 若上下文不足、边界冲突或发现更大问题，执行器子智能体应停止扩张并反馈主智能体等待再分派
- 若评估发现问题，主智能体需明确是否继续修复、调整方案或升级问题

## 与渐进式加载的关系

- 只有在任务涉及多角色协作、循环修复、执行后验证时，才优先加载本规则
- 若任务还涉及子智能体分派边界、验收模板和例外条件，需继续加载 `subagent-delegation-rule.md`
- 若只是简单只读分析任务，可不强制引入完整闭环流程
