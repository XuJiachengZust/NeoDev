# 元数据单一事实来源 Rule

## 目标

在资源类型、字段展示名、筛选字段、资格约束和共表多资源场景下，先确定事实来源的所有权，再决定前后端、网关和数据库的实现边界，避免别名散落、兜底过多和口径漂移。

## 触发场景

命中以下任一场景时，应补读本规则：

- 前端维护资源类型别名、字段别名或枚举兜底
- 同一个业务名称在前端、后端、数据库中各自维护一份
- 资源筛选字段名称与资源页展示名称容易不一致
- 多个资源类型落在同一张底表，需要固定条件区分
- `is_management` 这类稳定资格约束散落在多层代码中

## 基本原则

- 先确定所有权，再扩散实现。
- 展示名与编码分离，名称服务于展示，编码服务于契约与查询。
- 稳定业务约束优先沉淀到元数据、配置或明确契约中，不散落在多层兜底逻辑里。
- 若已有单一事实来源，不再额外维护平行口径。

## 所有权判断顺序

遇到名称、字段或过滤规则不一致时，优先判断其所有权落在以下哪一层：

1. 元数据表或初始化资源
2. 明确配置文件
3. 网关或 API 契约
4. 领域服务中的稳定映射

只有前几层都无法承载时，才考虑放在页面本地兜底，并明确说明其临时性。

## 使用要求

- 开始实现前，先写明“本次名称 / 字段 / 过滤条件的事实来源是什么”。
- 若多个资源共用一张底表，应优先通过元数据中的固定条件或表达式做记录级区分，而不是页面侧按表名粗分。
- 若某个资格条件对候选、绑定、查询都稳定成立，应优先放进元数据或统一配置，而不是分别散落在前端过滤和后端 where 条件里。
- 前端展示应优先使用后端或元数据返回的名称，不把本地别名作为主口径。

## 典型检查项

1. 资源类型名称是否只有一个稳定来源
2. 规则字段展示名称是否直接来自事实来源
3. 字段编码与展示文案是否被混用
4. 共表多资源是否靠记录级条件区分，而不是整表兜底
5. 纳管约束、启停约束、资格约束是否集中维护

## 禁止事项

- 在前端长期维护业务名称主口径，同时后端和数据库也各有一份
- 用多个局部别名来掩盖事实来源不清的问题
- 把稳定资格约束散落到多个页面和多个 SQL 条件里
- 明明已有元数据或配置入口，却继续新增页面本地兜底枚举

## 与其他规则的关系

- 若问题还涉及字段新增、删除、改名或契约收口，继续结合 `cross-layer-contract-change-rule.md`
- 若还未确定当前最可信的信息源，先结合 `reference-source-rule.md`
