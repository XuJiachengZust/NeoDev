# Git Rule

## 目标

统一仓库内与 harness engineering 相关的提交写法、拆分原则和多仓库协作边界。

## 基础规则

- 与本仓库协作时，说明、提交建议、规则示例优先使用中文
- `harness`、`rule`、`prompt`、`tool` 属于正式工程治理资产，必须纳入 Git 管理
- 不把这类资产当作临时文档放在 `docs/` 中
- 当前顶层目录可能是聚合工作区，下面的子项目可能各自拥有独立 Git 仓库；提交前必须先识别当前改动属于哪个仓库
- 不把顶层仓库、子项目仓库、嵌套仓库的改动混在同一个提交动作里

## 提交标识

- 仅修改 `harness/rule/prompt/tool` 时，使用 `chore(harness): ...`
- 业务代码与 harness 同时改动时：
  - 若 harness 变更可独立审阅，应拆分为单独的 `chore(harness): ...`
  - 若 harness 仅为业务改动的配套补充，可以跟业务提交放在一起，但提交说明要点明“同步沉淀 harness”

## 多仓库要求

- 若顶层目录下存在多个独立子项目仓库，应分别在对应仓库内查看状态、暂存、提交
- 若某次改动横跨多个子项目仓库，默认拆成多个提交，而不是在顶层目录做一个模糊的大提交
- 若顶层仓库只承担聚合工作区、治理规则、跨项目资料等职责，则这类改动应在顶层仓库提交

## 提交示例

- `chore(harness): 补充网关接口契约规则`
- `chore(harness): 明确聚合工作区与子仓库边界`
- `feat: 新增标签管理接口并同步沉淀 harness 规则`
- `fix: 修复标签管理网关调用并补充静态关联兼容`

## 拆分建议

- 目录骨架、共享规则、项目规则发生明显变化时，优先单独提交
- 若业务改动引出新的稳定约束，允许业务提交后补一个 `chore(harness): ...`
- 不要把生成物、编译产物、临时输出与 harness 资产混在同一个提交中
