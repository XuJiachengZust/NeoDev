# 跨层契约变更 Rule

## 目标

在字段新增、删除、改名、语义变更或请求/响应结构调整时，避免只改一层、只隐藏前端入口或只修局部映射，导致前端、网关、后端、数据库和验证链路长期残留不一致。

## 触发场景

命中以下任一场景时，应补读本规则：

- API 请求字段、返回字段新增、删除、改名
- DTO / VO / Entity / Mapper 字段收口
- 页面表单字段、状态字段、SDK 类型字段发生删改
- 数据库列、升级脚本、初始化资源与接口字段一起变化
- “前端不再展示”与“契约真的删除”之间需要做边界判断

## 基本原则

- 字段删除是契约删除，不是前端隐藏。
- 字段改名是跨层变更，不是单层替换。
- 若请求链路经过网关，先以网关对外契约为准，再看后端内部模型。
- 未列清单前，不进入大范围实现。
- 无明确兼容依据时，不保留长期双轨字段。

## 最低检查面

开始实现前，至少检查并记录以下层面：

1. 前端页面状态、表单模型、类型定义、SDK 或请求封装
2. 网关 API 描述文件、HTTP 方法、入参字段、出参结构
3. 后端 DTO、VO、Controller、Service、Entity、Mapper、转换器
4. 数据库存储结构、初始化资源、升级脚本、迁移路径
5. 验证用例、接口验证、页面联调和部署验收

若任务未命中某一层，也应显式记下“本层不涉及”而不是默认跳过。

## 推荐步骤

1. 先确认当前真实契约基准是网关描述、统一 SDK 还是裸后端接口。
2. 写一份跨层影响清单，记录字段新增 / 删除 / 改名 / 语义变化。
3. 标出每一层的保留项、删除项、映射项与兼容项。
4. 只有在清单稳定后，才进入实现与清理。
5. 完成后按清单逐项验收，而不是只验证页面是否还能打开。

## 删除场景要求

- 删除旧字段时，前端、网关、后端、数据库定义和验证用例都要同步收口。
- 若必须保留临时兼容，应写清：
  - 兼容原因
  - 兼容边界
  - 退出条件
- 不得以“先隐藏入口、后续再删”为默认完成状态。

## 改名与语义变更要求

- 改名时要明确新旧字段的契约对应关系，不得依赖隐式别名长期兜底。
- 语义变更时要确认：
  - 字段名是否需要同步变化
  - 展示文案、测试样例和迁移脚本是否仍成立
  - 旧数据是否需要迁移或清洗

## 禁止事项

- 只改前端展示，不改对外契约
- 只改 Controller 或 DTO，就假设页面联调可用
- 只改数据库列名，不核对请求/响应结构
- 没有升级路径就直接删除已部署环境仍依赖的字段
- 未经说明长期保留新旧字段双轨并行

## 与其他规则的关系

- 若请求链路经过网关，先结合 `gateway-api-contract-rule.md`
- 若任务开始前还未确定最小可信来源，先结合 `reference-source-rule.md`
- 若变更完成后需要清理旧实现，再结合 `code-cleanup-rule.md`
