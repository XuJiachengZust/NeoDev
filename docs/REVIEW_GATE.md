# NeoDev 提交前 Review Gate

## 目的

本门槛用于约束 Codex 在提交前的最小审核标准。未满足必过项时，不应提交。

## 使用方式

- 每个最小单元提交前都走一次本 Gate。
- 先自审，再提交；多人协作时，reviewer 按同一标准复核。
- 如果某项因环境原因无法执行，必须在提交说明中明确写出阻塞原因和替代判断。

## Gate 0：直接拦截项

出现以下任一情况，直接退回，不允许提交：

- 混入与目标无关的源码、文档、配置或格式化修改。
- 提交了生成物或本地产物，如 `web/node_modules`、`web/dist`、`__pycache__`、`.cursor/plans`、`docker/images/*.tar`。
- 提交了密钥、令牌、真实账号密码、私有路径或临时调试信息。
- 一个 commit 同时包含两个以上独立业务目标。

## Gate 1：范围门槛

必须全部满足：

- 改动目标可以用一句话解释清楚。
- `git diff --name-only --cached` 中的文件都与该目标直接相关。
- 没有“顺手修复”的旁支变更。
- 若工作区本来很脏，已明确只 stage 当前任务文件。

## Gate 2：正确性门槛

按改动类型检查：

- 后端接口改动：
  - 路由、服务、仓储、测试链路保持一致。
  - 错误码与返回体风格延续现有约定，通常为 `{"detail": ...}`。
- 数据库相关改动：
  - migration、读写逻辑、测试同时更新。
  - 不引入无法解释的兼容性破坏。
- 前端改动：
  - `web/src/api/client.ts` 的契约与后端返回一致。
  - 页面状态、空态、异常态至少覆盖一种。
- 文档改动：
  - 内容贴合当前仓库结构与现有命令，不写泛化流程。

## Gate 3：验证门槛

至少满足对应变更类型的最小验证要求：

| 变更类型 | 必跑项 |
| --- | --- |
| 仅文档 | `git diff --check` |
| 后端 router/service/repository | 对应 `pytest` 目标文件 |
| 前端 page/component/api | `cd web && npm run test:run` |
| 前端涉及构建路径或类型变更 | `cd web && npm run test:run` 和 `cd web && npm run build` |
| 前后端联动 | 后端对应 `pytest` + 前端测试，必要时再加前端 build |

补充要求：

- 优先跑与当前改动最相关的测试，不要求每次全量回归。
- 若改动触达公共基础层，需扩大验证范围到相邻领域。

## Gate 4：提交质量门槛

必须全部满足：

- commit message 使用 Conventional Commit 前缀。
- 提交说明能回答以下问题：
  - 改了什么
  - 为什么改
  - 怎么验证
  - 还剩什么风险
- 若存在已知未覆盖风险，必须显式写出，不得默认忽略。

## Gate 5：仓库卫生门槛

必须全部满足：

- `git status --short` 中当前提交范围清晰。
- 没有把锁文件、大文件、构建产物意外 stage 进去。
- 没有修改无关源码目录：
  - 后端任务不要顺手碰 `web/src`
  - 前端任务不要顺手碰 `src/service`
  - 文档任务不要顺手碰源码

## Reviewer 输出模板

提交前自审或人工 review 可按以下格式记录：

```text
目标:
范围:
验证:
结果:
风险:
结论: pass / revise / split
```

## 结论规则

- `pass`: 所有必过项满足，可以提交。
- `revise`: 目标正确，但存在验证、范围或说明不足，需要补齐后再提。
- `split`: 当前 diff 不是最小单元，必须先拆 commit。
