# 软件工程规则

## 1. 单一事实源

- 总 PRD 是业务对象、属性、术语、定义和跨功能业务规则的唯一来源。
- 子 PRD 只能引用总 PRD 的业务口径，不能重新定义。
- 冲突优先回到总 PRD 修订。

## 2. 可追踪

每条需求必须能追踪到：

- 事实源或待确认问题。
- 功能编号。
- 业务规则。
- 验收项。
- 测试场景。

最低追踪链路：

```text
事实源/问题 -> 需求/功能 -> 业务规则 -> AC -> 测试场景
```

## 3. 可测试

- 每个功能至少包含一个 P0 正向场景。
- 每个关键业务规则至少关联一个 AC。
- 每个功能必须覆盖关键异常场景和失败反馈。
- Given/When/Then 必须能被测试人员直接执行或转化为测试用例。
- 典型业务场景必须写到可执行粒度：触发条件、用户说法或业务背景、操作顺序、输入数据、读取事实、写入/变更事实、输出示例、下一步和验收关注点。
- 对“闭环”“流程”“同步”“路由”“提交”“检查”等需求，必须给出至少一个端到端业务场景，不得只写抽象流程或阶段名称。

## 4. 可实现

每个功能子 PRD 必须明确：

- 输入数据和输出数据。
- 数据读写边界。
- 状态变化。
- 交互入口和退出路径。
- 失败反馈。
- 接口候选和数据口径的确认状态。
- 典型场景中的数据变化和输出证据。

## 5. 可审查

- 已确认事实、代码事实、文档事实、AI 推断候选、待确认问题必须区分。
- 未确认内容不得使用确定性措辞。
- 不得把代码现状直接等同于产品目标，除非用户明确确认。

## 6. 图表要求

- 数据流图使用 Mermaid `flowchart`。
- 时序图使用 Mermaid `sequenceDiagram`。
- 图中节点名称必须使用总 PRD 中的标准业务对象或系统组件名称。
- 图中出现未确认对象或系统时，节点名后标注“待确认”。
