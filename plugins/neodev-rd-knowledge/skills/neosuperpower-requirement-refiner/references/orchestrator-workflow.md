# 主智能体编排流程

在进入独立评估前，主智能体必须完成 NeoDev 文档闭环：所有产物使用受控文档 front matter，运行 `sync_obsidian_links.py docs`，再运行 `validate_mvp_docs.py docs` 和 `validate_obsidian_docs.py docs`。任一校验失败时，先修复产物，不得进入“通过”收口。

requirement-refiner 默认不是单智能体线性任务。主智能体必须按最小必要上下文建立 DAG，并分派执行器和评估器子智能体。

## 1. 角色边界

- 主智能体：负责项目定位、范围裁决、DAG 拆分、分派、结果合并、冲突裁决、评估触发和最终回复。
- 执行器子智能体：负责被分派的单一产物或单一职责，不扩大范围，不替主智能体决定口径冲突。
- 评估器子智能体：负责只读验收，可读取命中子项目或仓库相关代码核对事实，不修改文件，不替主智能体收口。

## 2. 默认 DAG

```text
定位项目与输出路径
  -> 事实收集执行器
  -> 总 PRD 执行器
  -> 子 PRD 执行器
  -> 问题清单执行器
  -> 主智能体合并自检
  -> 独立评估器
  -> 修复循环或收口
```

可并行项：

- 在事实源明确后，多个子 PRD 执行器可按功能并行。
- 问题清单执行器可与子 PRD 执行器并行，但必须以总 PRD 当前口径为准。

不可并行项：

- 总 PRD 的业务对象、属性、术语和跨功能规则确定前，不得让子 PRD 执行器自行定义口径。
- 独立评估必须发生在主智能体合并自检之后。

## 3. 主智能体合并规则

- 总 PRD 是业务对象、属性、术语和跨功能规则的唯一事实源。
- 子 PRD 与总 PRD 冲突时，主智能体优先修订总 PRD 或要求子 PRD 执行器改回引用口径。
- 无来源编号或问题编号的确定性结论不得合并。
- 执行器提出的新问题只能进入 `99-open-questions.md` 或等待用户确认，不得直接升级为已确认需求。

## 4. 修复循环

评估器结论为“不通过”或“有风险待修复”时：

1. 主智能体按问题归属拆分修复任务。
2. 分派给对应执行器，不让评估器直接修复。
3. 主智能体合并修复结果。
4. 再次创建或复用独立评估器执行只读评估。

只有评估器给出“通过”，或用户明确接受残余风险，主智能体才能收口。
