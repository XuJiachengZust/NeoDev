# 页面验收测试

## 概览

这个 skill 用于执行有严格规范、有用户检查节点、有证据留痕的页面验收测试。

核心原则：每个测试结论都必须能从“测试方案 -> 测试用例 -> 浏览器操作 -> 截图 -> 网络返回 -> 数据库或日志证据 -> 测试报告”完整追溯。

## 职责边界

这个 skill 默认负责以下事项：

- 编写或补全测试方案
- 设计详细测试用例
- 执行页面验收测试
- 在失败时补充日志、数据库和代码定位证据
- 持续更新测试报告与测试状态
- 在关键节点向用户发起确认

这个 skill 默认不负责以下事项：

- 直接修复业务代码
- 在未获用户授权时扩展为开发任务
- 用“已定位问题”替代“已完成验收”
- 用接口成功替代页面成功
- 跳过对照样本、截图、网络记录或数据库校验
- 绕过用户检查节点直接继续下一阶段

## 协作模式

本 skill 推荐采用多智能体执行。

默认建议分工如下：

- 主智能体：负责规划、拆分、渐进加载控制、用户检查节点、监督执行、验收结论和最终收口
- 执行器子智能体：负责数据准备、SQL 校验、日志检查、代码定位、报告局部整理等具体执行任务
- 评估器子智能体：负责检查方案、用例、报告和证据是否完整，结论是否成立

主智能体默认不亲自承担大批量执行工作，除非任务很小、边界很清晰，且不存在明显并行收益。

## 何时使用

在下列场景使用：

- 任务要求在真实页面中完成交互验证
- 用户要求输出详细测试方案、详细测试用例或完整测试报告
- 测试过程必须留存逐步截图与关键网络证据
- 失败后需要结合日志、数据库状态和代码定位问题
- 明确要求使用浏览器 MCP 执行页面测试

在下列场景不要使用：

- 仅需编写单元测试或集成测试
- 只需要一次性人工检查且不要求证据留痕
- 纯接口校验，不涉及页面行为验证

## 必需产物

执行后必须产出或更新以下内容：

1. 测试方案文档
2. 测试报告文档
3. 截图目录
4. 网络证据目录
5. 需要时补充 SQL、日志和代码定位目录

产物根目录必须新建在产品目录下。产品目录指用户当前工作的产品仓库根目录，例如 `C:\Users\AH\IdeaProjects\dsc`。默认使用：

```text
<product-root>/acceptance-artifacts/<feature>-<yyyymmdd>/
```

禁止把测试方案、测试用例、测试报告、截图、网络证据、SQL、日志或代码定位记录写入 `harness/`、`docs/` 或具体子项目目录，除非用户明确指定其他产品根目录下的位置。

默认产物结构：

```text
<product-root>/acceptance-artifacts/<feature>-<yyyymmdd>/
  screenshots/
  network/
  sql/
  logs/
  code-notes/
```

## 渐进加载规则

不要一次性加载所有模板。按阶段渐进读取。

### 阶段 1：总控规则

先读取本文件，只理解流程、边界、检查节点和执行纪律。

仅当需要创建、复用或调整子智能体分工时，再读取 [`subagent-dispatch-template.md`](./subagent-dispatch-template.md)。

### 阶段 2：测试方案阶段

仅当需要编写、重写或补全测试方案时，再读取 [`test-plan-template.md`](./test-plan-template.md)。

输出结果：测试方案初稿。

完成后必须进入“用户检查节点 1”。

### 阶段 3：测试用例阶段

仅当用户确认测试方案后，再读取 [`test-case-template.md`](./test-case-template.md)。

输出结果：详细测试用例。

完成后必须进入“用户检查节点 2”。

### 阶段 4：场景补充阶段

仅当场景命中“规则配置 -> 执行任务 -> 页面可见 -> 数据库落库”链路时，再读取 [`dynamic-tag-template.md`](./dynamic-tag-template.md)。

输出结果：场景专属补充约束、补充用例和失败分类。

### 阶段 5：执行与取证阶段

执行浏览器测试、记录截图、网络、数据库和日志证据。

此阶段不额外加载模板，直接按已确认的方案和用例执行。

### 阶段 6：测试报告阶段

仅当开始编写或整理测试报告时，再读取 [`test-report-template.md`](./test-report-template.md)。

输出结果：正式测试报告。

完成后必须进入“用户检查节点 3”。

## 强制用户检查节点

这三个节点是强制阻塞节点，不得跳过。

### 用户检查节点 1：测试方案确认

触发时机：测试方案初稿完成后，详细测试用例设计前。

目标：确认范围、边界、环境、数据批次和验证口径。

必须询问用户：

`测试方案已整理完成，请确认测试范围、环境、数据批次和判定标准是否正确，确认后我再进入详细测试用例设计。`

边界：

- 未获确认，不进入详细测试用例阶段
- 不用“用户之前大概同意过”代替本节点确认

### 用户检查节点 2：详细测试用例确认

触发时机：详细测试用例完成后，浏览器执行前。

目标：确认用例矩阵、步骤粒度、页面验证点、网络验证点和数据库验证点。

必须询问用户：

`详细测试用例已整理完成，请确认是否按这套用例开始执行页面测试；如需增删资源类型、样本或验证点，请在这里调整。`

边界：

- 未获确认，不开始浏览器执行
- 不因“用户说尽快开始”跳过本节点

### 用户检查节点 3：测试报告确认

触发时机：测试报告初稿完成后，测试任务收口前。

目标：确认报告结构、结论表述、失败定位和后续补测需求。

必须询问用户：

`测试报告已更新完成，请确认当前结论、失败定位和证据是否满足要求；如需补测、重跑或补充报告结构，我再继续调整。`

边界：

- 未获确认，不将任务视为正式收口
- 不用“报告已经很完整”代替本节点确认

## 总体执行流程

必须按以下顺序执行：

1. 明确测试范围与边界
2. 确认测试环境、账号和数据批次
3. 读取测试方案模板并输出测试方案
4. 触发用户检查节点 1
5. 读取测试用例模板并输出详细测试用例
6. 触发用户检查节点 2
7. 视场景按需读取动态标签模板
8. 准备测试数据与产物目录
9. 串行执行浏览器步骤
10. 每一步保存截图和网络证据
11. 每个用例结束后立刻更新测试状态
12. 失败用例立即进入定位流程
13. 完成数据库与日志校验
14. 读取测试报告模板并输出正式测试报告
15. 触发用户检查节点 3

不要跳步，不要把报告拖到最后一次性补写，不要绕过用户确认。

## 执行阶段规范

执行时遵守以下硬规则：

- 页面动作必须串行执行
- 一个步骤只承载一个主断言
- 页面结论、网络结论、数据库结论分开记录
- 每一步至少一张截图
- 每一步都必须有对应网络记录
- 页面未发生变化时，也要截图证明“未变化”
- 未触发新请求时，也要记录“本步骤未触发新的业务请求”
- 不能把多个页面动作合并成一个步骤来减少证据量

## 失败定位规范

用例失败时，不能只写“页面失败”。

必须按以下顺序补证据：

1. 失败截图
2. 关键网络返回
3. 任务日志或服务日志
4. 数据库状态
5. 相关代码位置

失败分析必须回答以下问题：

- 用户做了什么操作
- 页面实际展示了什么
- 关键请求返回了什么
- 数据库或日志证明了什么
- 最可能的代码故障点在哪里
- 当前失败属于规则命中问题、运行链路问题，还是页面查询问题

## 浏览器执行规则

浏览器 MCP 操作默认串行执行；只有在明确验证过不同浏览器上下文完全隔离时，才允许并行。

默认按共享浏览器上下文处理。

- 页面交互：串行
- 截图采集：串行
- 与页面步骤绑定的网络抓取：串行
- 报告编写、SQL 准备、日志查看、代码阅读：可并行

## 多智能体分工

本 skill 推荐优先使用多智能体分工，主智能体主要负责规划和监督。

推荐拆分如下：

- 主智能体：负责阶段控制、模板渐进加载、用户检查节点、浏览器执行顺序、报告更新和最终判定
- 执行器子智能体：负责 SQL 校验、日志检查、代码定位、测试数据预检查
- 评估器子智能体：负责检查方案、用例和报告的完整性，以及证据是否缺失

### 主智能体职责

- 明确测试范围、边界和阶段目标
- 控制模板渐进加载顺序
- 决定哪些任务适合分派给执行器或评估器
- 维护用户检查节点，不绕过确认
- 汇总执行结果并给出最终验收结论

### 主智能体不应承担的默认职责

- 长时间逐项整理测试数据
- 大批量日志、SQL、代码定位细活
- 在可分派情况下独自承担报告填充和证据整理

### 分派原则

- 浏览器会话仍由单一智能体串行驱动，避免页面上下文相互干扰
- 与浏览器无强耦合的工作优先分派，例如数据准备、日志分析、SQL 校验、代码定位、报告审阅
- 主智能体负责监督，不用执行器自验收代替独立评估
- 需要统一分派话术时，按需加载 [`subagent-dispatch-template.md`](./subagent-dispatch-template.md)

不要让多个智能体同时驱动同一个浏览器会话。

## 常见错误

- 一上来加载所有模板，导致上下文过重
- 没有先让用户确认测试方案，就直接写详细用例
- 没有先让用户确认详细用例，就直接开始执行
- 测试报告写完后不回到用户确认，直接收口
- 把接口成功当成验收成功
- 只截最终页面，不截每一步
- 忘记准备对照样本
- 失败分析只有现象，没有日志、数据库和代码定位

## 完成检查单

- 已按阶段渐进加载模板
- 已完成用户检查节点 1
- 已完成用户检查节点 2
- 已完成用户检查节点 3
- 测试方案、测试用例、测试报告三类文档齐全
- 每一步都有截图
- 每一步都有网络证据
- 适用时每个用例都有数据库校验
- 每个失败步骤都有失败证据和定位说明
- 最终结论能够区分运行链路、页面查询链路和用户视角结论
