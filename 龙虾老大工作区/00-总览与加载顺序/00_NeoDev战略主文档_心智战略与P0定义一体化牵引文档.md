# NeoDev 战略主文档：心智战略与 P0 定义一体化牵引文档

日期：2026-03-30  
状态：主文档 / 当前上游牵引版本  
用途：作为 NeoDev 后续产品战略规划、P0 细化、路线图设计、验证设计与执行拆解的统一上游输入。

---

# 一、先给结论

## 1.1 NeoDev 是什么

**NeoDev 不是“又一个 AI 工具”，也不是“把文档、任务、代码硬拼在一起的平台”。**

NeoDev 的正确定义是：

> **AI 时代的人机协作研发闭环层。**

它要把原本散落在文档、聊天、任务系统、代码仓库、评审流程里的 **需求、上下文、计划、执行、证据、验收**，重新组织成一条可追踪、可审查、可放行、可复用的研发链路。

## 1.2 NeoDev 为什么存在

因为 AI 已经进入研发，但多数团队的工作方式还停留在旧时代：
- 需求靠人解释
- 上下文靠人转述
- AI 只在局部被调用
- 执行过程黑箱化
- 结果缺少证据链
- 验收靠负责人兜底
- 做完之后组织几乎没有沉淀出可复用能力

所以今天的核心矛盾，已经不是“AI 会不会生成”，而是：

> **如何让 AI 被可靠地纳入正式研发闭环，而不是成为一个更强但更难管的局部生成器。**

NeoDev 就是为这个断裂带而存在。

## 1.3 NeoDev 要改变用户什么心智

NeoDev 要推动用户从旧心智迁移到新心智。

### 旧心智
- 需求先讨论，执行时再慢慢理解
- 上下文靠老员工和负责人脑补
- AI 给结果就行，后面人再补解释
- 完成比可审查更重要
- 验收更多靠感觉和口头共识
- 一次任务做完就散，不会自然形成组织资产

### 新心智
- 需求必须先被压成目标、边界和验收标准
- 上下文应被结构化聚合，而不是靠临时转述
- AI 必须先计划、再执行
- 结果必须天然附带证据、风险和未覆盖项
- 人的价值从重复执行转向判断、放行与责任承担
- 每次任务完成都应该增强团队未来的执行能力

NeoDev 真正想占据的不是某个单点功能偏好，而是：

> **AI 时代研发团队的默认工作方式定义权。**

## 1.4 P0 产品定义是什么

NeoDev 的 P0 不做大而全平台，只打透一条最小但完整、足够可信、能被团队采纳的人机协作研发闭环：

> **模糊需求输入 → 结构化对象包 → 上下文聚合 → 计划审批 → 执行结果对象化 → 证据化评审 → 验收放行**

## 1.5 P0 为什么这样收敛

因为 NeoDev 的早期胜负，不取决于“功能够不够多”，而取决于它能不能让团队第一次真实感受到：

1. 复杂需求真的更容易变成可执行计划；
2. AI 输出真的更容易被团队信任和放行；
3. 负责人真的更少靠自己搬运上下文和背锅；
4. 一次任务真的开始沉淀未来可复用的组织资产。

所以 P0 必须优先打透“闭环价值”最强的链路，而不是铺开做广谱功能集合。

## 1.6 后续产品规划应如何从这份文档往下展开

后续所有规划都应遵守同一条下钻链路：

> **心智目标 → 战略定位 → P0 闭环定义 → 对象与状态机 → 页面与交互 → 执行批次 → 验证设计 → 路线图扩展**

也就是说，后续规划不应再从“还能加什么功能”出发，而应从下面三个问题出发：

1. 这个新能力是否强化了 NeoDev 的闭环层定位？
2. 这个新能力是否减少了需求、上下文、执行、证据、验收之间的断裂？
3. 这个新能力是否让团队更容易形成新的默认工作方式？

如果答案不是明确的“是”，就不应优先进入上游路线图。

# 二、NeoDev 的战略命题

## 2.1 NeoDev 面对的真实问题，不是工具少，而是链路断

今天的研发团队并不缺工具。缺的是一条能让 AI 真正进入正式协作的可信链路。

现状通常是：
- 需求在 PRD、会议纪要和聊天里
- 上下文分散在文档、代码、历史任务和口头传承里
- AI 在局部生成代码、文案或分析
- 结果再被人工搬运到评审、测试和验收流程里
- 最终责任仍由负责人用人脑兜住

这条链路的问题不在单点，而在连接处：
- 文档到计划断
- 计划到执行断
- 执行到证据断
- 证据到验收断
- 验收到复用断

NeoDev 的战略价值，正是在这些断点上建立新的默认结构。

## 2.2 NeoDev 真正的竞争对象

NeoDev 真正要替代的，不是某一个具体产品名，而是三层旧方式：

### 第一层：碎片化研发协作方式
- 需求在文档里
- 讨论在 IM 里
- 任务在项目系统里
- 代码在仓库里
- 验收在会议、口头同步或截图里

### 第二层：工具之间的断裂链路
- 没有统一对象承载目标、边界、证据和验收
- 没有把 AI 输出自然纳入共享评审的正式入口
- 没有把一次任务沉淀成未来可复用能力的机制

### 第三层：组织对“靠人脑拼上下文”的惯性依赖
- 老成员记住关键背景
- 负责人反复解释边界
- 决策依据埋在聊天记录里
- 评审和复盘不能稳定回看

所以 NeoDev 的主要战场，不是和单个工具做功能赛跑，而是：

> **替代碎片化、转述型、上下文高损耗的研发协作方式。**

## 2.3 NeoDev 应占据的战略位置

NeoDev 应争取的 system position 不是代码事实源，不是文档中心，也不是任务板替代，而是：

> **研发闭环编排层 / 人机协作执行中枢。**

它连接的是：
- 需求与执行
- AI 输出与人工验收
- 当前任务与未来复用
- 分散上下文与最终责任链路

这决定了 NeoDev 的产品边界：
它可以连接很多层，但不必在 P0 里替代所有层。

# 三、NeoDev 要改变的用户心智

## 3.1 要改写的不是工具使用偏好，而是工作方式

NeoDev 不是在争夺“用户更喜欢哪个聊天框”或“哪个 AI 生成得更快”。

它要改写的是研发团队对以下问题的默认回答：
- 需求怎样才算可以开始做？
- 上下文应该由谁来准备？
- AI 在正式流程里到底扮演什么角色？
- 什么样的结果才配进入 review 和验收？
- 一次任务做完后，团队到底留下了什么？

## 3.2 NeoDev 期望形成的新默认工作流

### 第一步：先把需求压成可执行意图
需求不能只是一段描述，而必须变成：
- Goal
- Boundary
- Success Criteria
- Risks
- Open Questions

### 第二步：系统提供共享上下文
把相关文档、历史任务、代码模块、设计与讨论记录聚到同一个工作对象下，让执行不再依赖口头补全。

### 第三步：AI 先提交计划，而不是直接黑箱执行
先给出：
- 任务拆解
- 依赖关系
- 风险点
- 待确认项
- 验收建议

### 第四步：执行结果必须对象化
不是一句“做完了”，而是生成结果对象页，明确展示：
- 做了什么
- 没做什么
- 依据是什么
- 风险和未覆盖项是什么
- 应如何验收

### 第五步：人对关键节点负责任
人类角色不再负责手工搬运所有细节，而是负责：
- 审批计划
- 判断边界
- 审查证据
- 放行或退回

### 第六步：完成即沉淀
任务做完后不仅要有状态，更要留下：
- 决策依据
- 执行证据
- 放行理由
- 可复用模板和经验

## 3.3 NeoDev 的心智判断标准

如果用户开始自然接受下面这些判断，说明 NeoDev 正在占领心智：
- “需求必须先结构化，不然不该直接进入执行。”
- “AI 结果没有证据链，就不该直接被信任。”
- “评审应该围绕结果对象，而不是围绕聊天截图。”
- “每做完一次任务，组织都应该更聪明一点。”

# 四、NeoDev 的产品定义：从战略收到 P0

## 4.1 P0 的一句话产品定义

> **NeoDev P0 是一条最小但完整的人机协作研发闭环，用来把模糊需求转成可审查、可放行、可沉淀的执行结果。**

## 4.2 P0 的目标用户

优先服务三类用户：

1. **Tech Lead / 工程经理**
   - 对目标、风险、质量、放行负责
   - 最怕任务跑偏、AI 不可控、结果不可审

2. **高 AI 使用密度的资深工程师 / 全栈工程师 / 产品工程师**
   - 已经把 AI 用到编码、分析、文档、调试中
   - 对上下文丢失和多工具切换高度敏感

3. **小到中型、高迭代、愿意重构工作流的产品团队**
   - 足够敏捷
   - adoption 成本较低
   - first win 更容易转成团队级习惯

不优先服务：
- 只想自动写代码的个人用户
- 没有明确验收纪律的团队
- 大型复杂企业的第一阶段切入

## 4.3 P0 的核心产品目标

P0 不是证明 NeoDev 功能多，而是证明一件事：

> **团队真的愿意让 AI 进入正式研发闭环，并愿意基于 NeoDev 里的共享对象、证据与验收记录做放行。**

具体目标分解为四个：
1. 把模糊需求更快转成可执行对象；
2. 把分散上下文聚合到同一任务对象；
3. 强制“先计划、后执行”；
4. 把执行结果变成可评审、可证据化、可放行的结果对象。

## 4.4 P0 的非目标

P0 明确不做：
- 大而全项目管理替代
- 通用 IDE / 编码助手替代
- 复杂组织治理与多级审批
- 全量组织知识飞轮自动化
- 大企业长流程适配
- 以模型能力强弱作为核心卖点

这不是能力不足，而是战略收敛：
P0 的目标是先证明“闭环层成立”，而不是先证明“覆盖面足够广”。

# 五、P0 为什么必须这样收敛

## 5.1 因为 NeoDev 的 first win 必须足够锋利

一个好的 P0，必须在一次任务里就让用户感受到旧方式明显更差。

最强 first win 不是“AI 又帮我省了几步操作”，而是：
- 以前需要多轮解释的需求，现在能快速变成可执行计划；
- 以前 AI 做完还得人工重述，现在结果天然可评审；
- 以前负责人靠记忆兜底，现在可以基于证据做放行；
- 以前做完就散，现在能看到组织资产开始积累。

## 5.2 因为 P0 的本质是建立信任结构

NeoDev 与普通 AI 工具的差别，不在“会不会生成”，而在是否建立了下面三种信任：

1. **输入信任**：目标和边界清楚，不会一开始就做歪；
2. **过程信任**：AI 不是黑箱，而是先计划、再执行；
3. **结果信任**：产物不是一句完成，而是带证据、风险和验收入口。

P0 只有围绕这三种信任设计，才可能形成后续 adoption。

## 5.3 因为如果一开始做大，产品会迅速失焦

如果 P0 同时去做：
- 全面项目管理
- 全面知识管理
- 全面代码协作
- 全面部署与监控

那么 NeoDev 很快就会重新被理解成：
- 另一个任务板
- 另一个文档系统
- 另一个 AI 工作台

这会直接稀释“闭环层”定位。

所以 P0 的收敛不是保守，而是为了把战略判断变成可被用户感知的最短闭环。

# 六、P0 闭环骨架：能力、对象、栅栏

## 6.1 P0 四个一级能力

P0 建议稳定收敛为四个一级能力：

1. **需求结构化**
   - 把原始需求转成可执行对象包
2. **上下文聚合**
   - 把文档、历史任务、代码、设计、讨论连接到同一对象
3. **计划生成与执行管控**
   - 让 AI 和人围绕显式计划推进
4. **结果评审与证据化验收**
   - 让结果可审、可追踪、可放行

这四个能力正好承接 NeoDev 的核心命题：
**从意图，到执行，再到证据与责任。**

## 6.2 P0 的核心对象

后续产品设计应围绕以下对象，而不是围绕聊天消息：

### 主容器对象
- **Work Item**：一次工作的主对象，承载从需求到放行的主线闭环

### 阶段子对象
- **Plan**：一版正式执行计划
- **Artifact**：一轮执行产物
- **Acceptance**：围绕某个产物的验收与放行记录

### 强约束字段 / 从属对象
- Goal
- Boundary
- Success Criteria
- Context Reference
- Task
- Evidence
- Risk

这意味着 NeoDev 的产品哲学是：

> **正式协作围绕结构化对象发生，而不是围绕零散对话发生。**

## 6.3 三道栅栏

P0 的可信闭环应由三道栅栏保证：

### 第一栅栏：清晰度栅栏
解决“需求还没清楚就开始推进”的问题。

通过条件：
- Goal 明确
- Boundary 明确
- Success Criteria 至少成型
- Open Questions 被显式列出
- Context References 达到最小挂接标准

### 第二栅栏：审批栅栏
解决“计划没人拍板就直接进入执行”的问题。

通过条件：
- Plan 已形成
- 关键待确认项已处理或被接受
- 负责人已批准进入执行

### 第三栅栏：证据栅栏
解决“结果不可审、不可放行”的问题。

通过条件：
- 结果页存在
- 有目标与计划关联
- 有证据项
- 有风险与未覆盖项说明
- 有验收清单和放行入口

这三道栅栏决定了 NeoDev 不是一个“更能自动干活的黑箱”，而是一个“更能让团队放心放行的闭环层”。

# 七、P0 的最小核心场景

## 7.1 场景一：从模糊需求到可执行计划

这是最优先的入口场景。

### 旧痛
- 需求文档长，但可执行内容不清
- 角色理解不一致
- AI 会总结，但不会稳定地产出可审计划

### NeoDev 的新方法
输入需求后，系统自动完成：
- 抽取目标、边界、验收草案
- 识别风险、未知项、待确认问题
- 聚合相关上下文
- 产出任务拆解、依赖和执行建议
- 明确哪些点必须人确认

### 用户应感知到的新价值
> “需求不该停留在讨论层，而应该直接变成一个可审查的执行对象。”

## 7.2 场景二：AI 执行结果的共享评审与证据化验收

这是 NeoDev 建立信任的核心场景。

### 旧痛
- AI 说做完了，但团队不知道到底改了什么
- 评审依赖聊天、截图或口头同步
- 负责人很难基于结构化依据放行

### NeoDev 的新方法
每次执行后自动形成结果页，展示：
- 本轮做了什么 / 没做什么
- 关联目标和计划
- 文档、diff、测试、预览等证据
- 风险与未覆盖项
- 评论线程
- 验收清单
- 放行 / 退回记录

### 用户应感知到的新价值
> “AI 结果不该只是一个回答，而应该像一个正式 Artifact 一样被共享评审和放行。”

## 7.3 为什么 P0 优先只打这两端

因为这两端最能体现 NeoDev 的差异：
- 前端解决“怎么开始”
- 后端解决“怎么相信、怎么放行”

中间执行层在 P0 可以先适度借助现有工具与人工协作，不必一开始就做成全栈平台。

# 八、后续产品规划该如何从这份主文档往下展开

## 8.1 下游规划的标准展开顺序

所有后续产品规划，建议统一按以下层级往下展开：

### Level 1：心智与战略层
回答：
- 我们到底在定义什么新工作方式？
- 这次规划是在强化哪个心智判断？

### Level 2：闭环层定义
回答：
- 这次能力落在哪个闭环节点？
- 它减少的是哪种断裂？
- 它帮助建立的是哪种信任？

### Level 3：对象与状态机层
回答：
- 新能力落在 Work Item / Plan / Artifact / Acceptance 的哪一层？
- 会新增什么状态、动作、证据或约束？
- 是否改变三道栅栏的规则？

### Level 4：页面与交互层
回答：
- 用户在哪个页面完成动作？
- 哪些字段必须显式？
- 哪些阻断和提醒必须前置？

### Level 5：执行与任务包层
回答：
- 这次需求如何拆到批次任务里？
- 哪部分能直接开发？
- 哪部分需要先做 demo 或验证？

### Level 6：实证验证层
回答：
- 这次能力要验证什么核心假设？
- 目标用户是否能在短时间内复述价值？
- 它是否真的降低了沟通、评审或放行成本？

## 8.2 后续路线图的判断原则

任何进入路线图的新能力，都应过三问：

1. **它是否强化 NeoDev 的闭环层定位，而不是把产品拉回旧类别？**
2. **它是否让需求、上下文、计划、执行、证据、验收之间的链路更短、更清楚、更可信？**
3. **它是否有助于用户形成“先结构化、先计划、结果附证据、人负责放行”的新习惯？**

## 8.3 P1 / P2 的自然展开方向

在 P0 成立之后，更合理的扩展方向不是“做更多杂功能”，而是顺着闭环继续加深：

### P1 候选方向
- 陌生项目 / 模块的上下文进入与导览
- 更强的结果 diff 与版本比较
- 更完整的审批意见与退回原因结构化
- 缺失上下文提醒与质量提示

### P2 候选方向
- 更强的经验沉淀与模板复用机制
- 组织级工作法沉淀
- 更系统的 adoption 支持与治理能力
- 更深的跨工具编排与组织记忆增强

判断标准始终不变：
**不是为了扩功能而扩功能，而是为了让闭环更可信、更低损耗、更能复用。**

# 十一、最终结论

把整份主文档压缩成几句话，就是：

1. **NeoDev 的机会不在更强生成，而在更可信闭环。**
2. **它真正要替代的不是某个工具，而是碎片化、转述型、上下文高损耗的研发协作方式。**
3. **NeoDev 要改写的是研发团队如何与 AI 协作的默认心智。**
4. **P0 必须收敛到一条最小但完整的闭环：从模糊需求到可执行计划，再到证据化评审与验收放行。**
5. **后续所有产品规划，都应从这份主文档往下展开，而不是从功能列表往上拼装。**

如果这五句话成立，NeoDev 后续的 PRD、路线图、原型、验证和执行，就有了统一的上游牵引。
