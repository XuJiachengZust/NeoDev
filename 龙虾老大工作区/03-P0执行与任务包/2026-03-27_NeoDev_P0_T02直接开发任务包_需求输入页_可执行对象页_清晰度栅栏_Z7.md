# 一、文档目的与结论先行

## 1.1 本文档解决什么问题
本文档把 P0-BATCH1-T02 从“任务说明”继续细化为 **可以直接分发给产品/前端/后端开工的最小开发任务包**。

聚焦范围只有三件事：
1. 需求输入页
2. 可执行对象页
3. 清晰度栅栏（Clarity Gate）

目标是把用户输入的原始需求，稳定推进为一个满足 `plan_ready` 条件的 Work Item，而不是停留在摘要或聊天产物层。

## 1.2 T02 的最小成功定义
T02 完成后，系统必须支持以下最小闭环演示：
1. 在需求输入页粘贴原始需求并创建 Work Item；
2. 在可执行对象页查看并编辑结构化字段；
3. 补充最小上下文与风险信息；
4. 触发清晰度栅栏校验；
5. 若条件满足，Work Item 从 `draft/clarifying` 进入 `plan_ready`；
6. 若条件不满足，系统明确给出结构化阻断原因，并停留在对象页继续补齐。

## 1.3 本任务的明确边界
**包含：**
- Work Item 在 M1 阶段的字段与最小数据结构
- 需求输入页模块、动作、校验
- 可执行对象页模块、动作、校验
- 清晰度栅栏触发、阻断、放行、回退语义
- M1 用于联调/回归的样例与验收步骤

**不包含：**
- Plan 生成逻辑
- 审批动作与审批栅栏
- Artifact / Evidence / Acceptance 落地
- 复杂推荐、相似案例召回、多角色权限
- 真实 AI 抽取质量优化策略

一句话边界：**T02 只负责把 Work Item 做成“可进入计划”的对象，不负责后续计划与执行。**

# 二、T02 的对象与页面基线

## 2.1 涉及主对象
### 主对象
- `Work Item`

### 强约束字段 / 从属对象
- `Goal`
- `Boundary`（`boundary_in` / `boundary_out`）
- `Success Criteria`
- `Open Questions`
- `Risks`
- `Assumptions`
- `Context References`

## 2.2 涉及页面
- 任务列表 / 首页（只做最小状态摘要联动）
- 需求输入页
- 可执行对象页

## 2.3 T02 必须遵守的状态语义
- `draft`：刚创建 Work Item，只完成原始输入落库
- `clarifying`：结构化对象仍待澄清，尚未通过清晰度栅栏
- `plan_ready`：已满足进入计划阶段的前置条件
- `blocked`：只用于外部依赖/关键前提缺失，不用于普通字段未补全

## 2.4 本阶段最核心的系统约束
1. `raw_input` 必须保留原始版本，不允许被结构化内容覆盖。
2. 需求输入页只做轻输入，不承载重型完整编辑。
3. Goal / Boundary / Success Criteria / Open Questions / Context 的主编辑入口在可执行对象页。
4. 没通过清晰度栅栏，不得进入 `plan_ready`。
5. 阻断必须结构化展示，不允许只有一句笼统“信息不足”。

# 三、T02 最小开发拆分总览

## 3.1 推荐开发顺序
推荐按以下 6 个子任务顺序推进：

1. **T02-A：Work Item M1 字段骨架与状态约束落地**
2. **T02-B：需求输入页最小创建流**
3. **T02-C：可执行对象页主结构与编辑流**
4. **T02-D：清晰度栅栏判定器与阻断反馈**
5. **T02-E：首页/列表最小状态摘要联动**
6. **T02-F：M1 回归样例与验收脚本**

原因：
- 先把对象骨架立稳，再做页面；
- 先让创建和编辑成立，再加 Gate；
- 最后补列表联动与回归，形成完整 first win。

## 3.2 子任务之间的依赖关系
```text
T02-A 对象骨架
  ↓
T02-B 需求输入页创建流
  ↓
T02-C 可执行对象页编辑流
  ↓
T02-D 清晰度栅栏
  ├─ 依赖 T02-C 的字段输入
  └─ 反向驱动 T02-E 的状态展示
      ↓
T02-E 列表状态摘要
      ↓
T02-F 回归样例与验收
```

**不包含：**

5. `block_reason` 能标识清晰度栅栏阻断原因。

### 风险
1. 字段先天建得太散，后续页面反复改口径；
2. 用单字段文本偷懒，后续无法支持结构化 Gate；
3. 提前混入 Plan 语义，导致对象边界变脏。

- 标题输入或自动生成标题占位
- `task_type` 选择
- `source_type` 选择
- 初始上下文挂接入口（可简化为链接/引用列表）
- “创建并进入对象页”动作

**不包含：**
- Goal/Boundary 的完整深度编辑
- Plan 入口
- 审批动作

### 涉及页面 / 对象
**页面：**
- 需求输入页

**对象：**
- Work Item
- 初始 Context References

### 页面模块建议
1. 原始需求输入框
2. 来源类型选择器
3. 任务类型选择器
4. 初始上下文挂接区（最小可先支持 URL/文本引用）
5. 创建按钮
6. 错误提示与创建成功跳转

### 核心交互
- 用户粘贴原始需求；
- 选择来源类型/任务类型；

- 点击创建后生成 Work Item；

4. 页面轻量，不要求用户在此页填完所有结构化字段；
5. 首页/列表能看到新建对象。

1. 入口页过重，用户创建成本过高；
2. 创建即要求填完整对象，违背 first win；
3. 初始上下文入口缺失，后续对象页上下文为空心化。

- Goal 区
- Boundary 区
- Success Criteria 区
- Open Questions 区
- Risks / Assumptions 区

- 缺失提醒区

**不包含：**

- 审批意见
- 结果/证据/验收

### 涉及页面 / 对象
**页面：**
- 可执行对象页

**对象：**
- Work Item
- Goal
- Boundary
- Success Criteria
- Open Questions
- Risks
- Assumptions
- Context References

### 页面模块建议
1. 顶部摘要：标题、状态、清晰度状态、最近更新时间
2. Goal 卡片：目标定义与编辑
3. Boundary 卡片：做什么 / 不做什么
4. Success Criteria 列表
5. Open Questions 列表（支持关闭/接受风险/保留）
6. Risks / Assumptions 列表
7. Context References 列表
8. 缺失项提醒面板

### 核心交互
- 用户补 Goal / Boundary / Success Criteria；
- 用户处理 open questions；
- 用户添加/删除/编辑 context refs；
- 用户查看当前缺失项；
- 用户触发清晰度校验；
- 系统返回 pass/block 结果。

### 状态变化
- 首次进入编辑：`draft → clarifying`
- 持续编辑：保持 `clarifying`
- 通过 Gate：`clarifying → plan_ready`
- Gate 失败：保持 `clarifying`

### 验收标准
1. Goal / Boundary / Success Criteria / Open Questions / Context References 都有明确编辑入口；
2. 页面能展示当前缺失项，而不是把所有错误都埋在提交后；
3. 用户可显式区分“未解决问题”和“可接受风险”；
4. 页面展示清晰度状态与下一步动作；
5. 不需要跳到其他页面就能补齐进入计划前所需的主要信息。

### 风险
1. 页面只展示摘要，不支持真正修订；
2. Goal / Boundary / Questions 分散到多个入口，导致主写边界不清；
3. Context 区缺少最小结构，后续 Gate 无法稳定判断。

### 推荐提交信息
- `feat(executable-brief): add work item editable detail page`

## T02-D：清晰度栅栏判定器与阻断反馈

### 任务顺序
第 4 个开发子任务，是 T02 的核心收口任务。

### 目标
把清晰度栅栏从“提示文案”做成真正的状态前置条件：只有在 Goal、Boundary、Success Criteria、Open Questions、Context、Risk 满足最小要求时，Work Item 才能进入 `plan_ready`。

### 边界
**包含：**
- Gate 触发时机
- 阻断规则
- 放行规则
- 结构化 block reason 返回
- 状态流转与回退语义

**不包含：**
- 审批栅栏
- 证据栅栏
- 智能推荐修复建议的高级能力

### 涉及页面 / 对象
**页面：**
- 可执行对象页
- 首页/列表（只读展示 gate 结果）

**对象：**
- Work Item
- Context References
- Risks
- Open Questions

### 触发时机
以下动作必须触发清晰度栅栏：
- 点击“进入计划”
- 点击“生成 Plan”（即便 Plan 页尚未实现，也要预留动作约束）
- 显式执行“校验是否可计划”

### 阻断条件
任一命中即 block：
1. `goal` 为空或过于模糊；
2. `boundary_in` 或 `boundary_out` 缺失；
3. `success_criteria` 为空；
4. 存在关键 `open_questions` 未关闭且未被接受；
5. `context_refs` 未达到最小挂接要求；
6. 存在高风险但未记录处理方式。

### 放行条件
同时满足才 pass：
1. Goal 清楚；
2. 做什么 / 不做什么清楚；
3. 至少一条 Success Criteria；
4. Open Questions 已关闭或转为接受风险；
5. 至少 1 条 Context Reference；
6. 风险已显式记录。

### 状态变化
- Gate fail：`clarity_gate_status = block`，Work Item 保持 `clarifying`
- Gate pass：`clarity_gate_status = pass`，Work Item `clarifying → plan_ready`

### 验收标准
1. Gate 规则可重复执行，结果稳定；
2. 阻断原因按结构化列表返回，而不是单段报错；
3. `plan_ready` 只能由 Gate pass 触发；
4. 当字段被再次改坏时，可重新回到 `clarifying/block`；
5. 列表页可看到该对象是“可计划”还是“待澄清”。

### 风险
1. Gate 过松，任何半成品都能过；
2. Gate 过重，正常 first win 也被卡死；
3. Block 原因不结构化，用户不知道补哪里。

### 推荐提交信息
- `feat(clarity-gate): add plan-readiness validation and block reasons`
- `feat(work-item): enforce clarifying to plan-ready transition by clarity gate`

# 五、T02 统一验收口径

## 5.1 最小验收演示脚本
1. 在需求输入页粘贴一段原始需求；
2. 选择来源类型与任务类型，创建 Work Item；
3. 跳转到可执行对象页；
4. 补齐 Goal、Boundary、Success Criteria；
5. 添加至少 1 条 Context Reference；
6. 处理 Open Questions 与 Risks；
7. 触发清晰度栅栏；
8. 若未补齐，页面展示结构化阻断原因并保持 `clarifying`；
9. 补齐缺失项后再次校验；
10. Work Item 进入 `plan_ready`，首页状态同步更新。

## 5.2 T02 完成的判断标准
只有同时满足以下条件，T02 才算真正完成：
1. 有稳定 Work Item M1 字段骨架；
2. 有可用的需求输入页创建流；
3. 有可用的可执行对象页编辑流；
4. 清晰度栅栏真的阻止非法进入 `plan_ready`；
5. 首页/列表能看见状态与阻断摘要；
6. 至少 3 条回归样例可重复演示。

# 七、主要风险与控制策略

## 风险 1：把 T02 做成“摘要页”，而不是“对象页”
控制：必须支持人工修订，不能只读。

## 风险 2：把需求输入页做成大而全表单
控制：入口页只保留轻输入与创建动作，重字段集中在对象页。

## 风险 3：清晰度栅栏变成弱提示
控制：`plan_ready` 只能由 Gate pass 触发。

## 风险 4：Context Reference 设计过重
控制：P0 只要求最小挂接能力，不要求复杂知识图谱。

## 风险 5：状态展示不透明
控制：首页必须展示状态、阻断摘要、下一步动作。

# 九、最适合先开工的前 3 个开发子任务

## 1. T02-A：Work Item M1 字段骨架与状态约束落地
原因：不先把对象骨架定住，后面的页面和 Gate 都会反复返工。

## 2. T02-B：需求输入页最小创建流
原因：这是 first win 的入口，没有创建流，整个 T02 无法真正跑起来。

## 3. T02-C：可执行对象页主结构与编辑流
原因：清晰度栅栏依赖这页的字段补齐与修订动作；这是 M1 的主舞台。

# 十、T02 拆分摘要（供派工时复用）

一句话摘要：

> T02 的本质不是做两个页面，而是把 Work Item 从原始需求推进成可计划对象；因此必须先立 Work Item M1 字段骨架，再打通需求输入页与可执行对象页，最后用清晰度栅栏把 `clarifying → plan_ready` 变成真正的系统约束。

最小闭环摘要：
- 入口页负责创建原始 Work Item；
- 对象页负责补 Goal / Boundary / Success Criteria / Questions / Risks / Context；
- 清晰度栅栏负责判断是否允许进入 `plan_ready`；
- 首页负责把卡点显性化；
- 样例包负责证明 first win 真的成立。
