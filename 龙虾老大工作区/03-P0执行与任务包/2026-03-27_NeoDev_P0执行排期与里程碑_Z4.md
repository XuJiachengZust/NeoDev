# 一、执行结论先行

## 1.1 本次排期的核心判断
NeoDev P0 不应按“功能堆叠”推进，而应按 **最小可信闭环** 推进。

因此执行顺序不应是：
- 先做很多页面；
- 再慢慢接对象；
- 最后补状态机与验收。

而应是：

> **先把 Work Item 主对象、强状态机与三道栅栏立起来，再把页面串上，再补证据化验收，最后再加效率增强项。**

这会使 P0 从第一天起就更接近 NeoDev 的真正产品承诺：
- 先计划，后执行
- 带边界推进
- 结果可审
- 决策可放行

## 1.2 建议采用的阶段拆法
按最小可用单元拆为 5 个阶段：

1. **M0：P0 骨架定盘**
2. **M1：需求结构化 + 可执行对象包可跑通**
3. **M2：计划生成与审批栅栏可跑通**
4. **M3：执行结果页 + 证据化验收可跑通**
5. **M4：闭环打磨、演示与实证准备**

其中：
- **必须先做**：M0 → M1 → M2 → M3
- **可并行穿插**：部分 UI、提示文案、演示脚本、测试样例、数据种子
- **可后置**：设计稿关联、讨论记录细化、自动相似案例召回、负责人建议、优先级建议、增强提示等 P0+ 能力

## 1.3 推荐节奏
若已有现成 NeoDev 工程基础，建议按 **2.5~4 周** 控制：
- Week 1：M0 + M1
- Week 2：M2
- Week 3：M3
- Week 4：M4 与补洞

若资源更紧，可按“先做演示级 P0”压缩到 2 周，但前提是明确只做一条 happy path，不追求完整覆盖。

# 二、排期设计原则

## 2.1 以对象和栅栏为主，不以页面数量为主
P0 的核心不是“有 6 个页面”，而是以下对象/状态真实成立：
- Work Item
- Goal / Boundary / Success Criteria / Risks / Open Questions
- Plan
- Artifact
- Evidence
- Acceptance
- Work Item / Plan / Artifact / Acceptance 状态机

## 2.2 先主链路闭环，再补增强体验
主链路必须优先保证：
1. 输入需求
2. 生成对象包
3. 补全上下文并满足清晰度栅栏
4. 生成计划并审批
5. 提交执行结果
6. 附证据验收并放行/退回

只要这条链不稳，其他增强都不应抢前。

## 2.3 每个阶段都要形成可演示成果
每个阶段结束时，必须能回答老板两个问题：
- 这阶段具体多了什么能力？
- 这能力是否已形成可以演示/验收的最小闭环？

## 2.4 默认把“可后置项”挡在门外
为了防止 P0 膨胀，以下内容默认后置，不得阻塞主排期：
- 多组织权限与复杂审批流
- 全量知识沉淀飞轮
- 自动召回相似案例
- 复杂角色分工系统
- 高级优先级算法
- 大而全首页治理视图
- 全面替代 Jira / Linear / IDE 的企图

# 三、总排期总览

## 3.1 里程碑总表

### 里程碑 M0：P0 骨架定盘
**目标**：把对象模型、状态机、栅栏、页面映射、验收口径定成统一工程基线。  
**输出**：统一的 P0 数据骨架与执行边界。  
**性质**：必须先做。  
**没有它的风险**：后续各子智能体会各做各的，最后很难拼成同一产品。

### 里程碑 M1：需求结构化闭环
**目标**：用户输入原始需求后，系统可生成可执行对象包，并完成最基础的人工修订与上下文挂接。  
**输出**：Work Item 从 `draft/clarifying` 到 `plan_ready` 的半闭环。  
**性质**：必须先做。  
**这是 P0 第一关键 first win。**

### 里程碑 M2：计划与审批闭环
**目标**：对象进入计划阶段后，系统能生成任务拆解、顺序、依赖，并通过审批栅栏进入执行。  
**输出**：Work Item 从 `plan_ready` 到 `approved/executing`。  
**性质**：必须先做。  
**这是 NeoDev 与黑箱 AI 的第一道差异化护城河。**

### 里程碑 M3：结果与验收闭环
**目标**：执行结果成为 Artifact，对应证据、风险、未覆盖项和 Acceptance 记录完整可审。  
**输出**：Work Item 从 `executing/review_pending` 到 `released/done` 或 `returned`。  
**性质**：必须先做。  
**这是 NeoDev 与普通聊天式 AI 工具拉开差距的第二道护城河。**

### 里程碑 M4：演示与实证就绪
**目标**：打磨一条完整 demo、补齐关键空洞、形成可对外/对老板审阅的版本。  
**输出**：稳定演示链路、测试样例、已知风险清单、实证脚本映射。  
**性质**：应做，但可在核心闭环打通后集中做。

# 四、分阶段详细排期

## M0：P0 骨架定盘（预计 2~3 天）

### 4.0.1 阶段目标
把 P0 的“共同语言”定死，避免后续实现时对象、状态、页面、验收口径互相打架。

### 4.0.2 本阶段必须完成
1. 明确 P0 一等对象字段最小集
2. 明确 Work Item / Plan / Artifact / Acceptance 状态机
3. 明确三道栅栏的入场条件
4. 明确页面与对象的映射关系
5. 明确每个里程碑的验收方式

### 4.0.3 最小可用任务单元

#### T0-1：输出 P0 统一对象字典
- 内容：Work Item、Plan、Task、Artifact、Evidence、Acceptance 的字段最小集
- 依赖：已有 PRD + Z2 状态机草稿
- 验收：能回答“每个页面到底在读写哪个对象、哪些字段”
- 性质：必须先做

#### T0-2：输出 P0 统一状态机规格
- 内容：状态枚举、合法流转、拦截规则、异常状态
- 依赖：T0-1
- 验收：形成状态流转图或状态规则文档，可供前后端共享
- 性质：必须先做

#### T0-3：输出 栅栏规则清单
- 内容：清晰度栅栏、审批栅栏、证据栅栏的进入条件与报错口径
- 依赖：T0-2
- 验收：每道栅栏都有清晰 allow / block 条件
- 性质：必须先做

#### T0-4：输出 页面-对象映射表
- 内容：需求输入页、对象页、计划审批页、执行结果页、验收放行页分别负责哪些字段和动作
- 依赖：T0-1, T0-2
- 验收：不存在“同一字段多页争夺主写入口”的冲突
- 性质：必须先做

#### T0-5：建立 P0 演示样例数据
- 内容：至少准备 1 条完整样例需求，贯穿后续所有里程碑
- 依赖：无
- 验收：后续每阶段都能用同一条样例回归演示
- 性质：可并行

### 4.0.4 本阶段完成标志
- 团队对 P0 主对象、状态、栅栏无重大歧义
- 后续所有实现任务可直接引用统一规格
- 可以开始正式进入 M1 开发

### 4.0.5 本阶段主要风险
- 风险：过度讨论抽象模型，迟迟不进入实现
- 控制：字段只保留 P0 最小集，不追求一次建全

## M1：需求结构化 + 可执行对象包（预计 4~6 天）

### 4.1.1 阶段目标
形成 P0 第一段 first win：把原始需求变成 **可执行对象包**，并能被人修订、补上下文、推进到 `plan_ready`。

### 4.1.2 本阶段必须完成
1. 需求输入页最小可用
2. 对象包生成能力最小可用
3. 可执行对象页最小可用
4. 上下文挂接最小可用
5. 清晰度栅栏可拦截

### 4.1.3 最小可用任务单元

#### T1-1：需求输入入口
- 内容：支持粘贴原始需求文本，基础任务类型选择
- 依赖：M0
- 验收：可创建 Work Item `draft`
- 性质：必须先做

#### T1-2：结构化抽取器 V1
- 内容：生成 Goal / Boundary / Success Criteria / Risks / Open Questions
- 依赖：T1-1
- 验收：至少对样例需求能稳定输出对象包
- 性质：必须先做

#### T1-3：可执行对象页 V1
- 内容：展示结构化字段，支持人工修订
- 依赖：T1-2
- 验收：用户可修改 Goal / Boundary / Success Criteria
- 性质：必须先做

#### T1-4：上下文挂接 V1
- 内容：至少支持文档关联、历史任务占位、代码范围占位
- 依赖：T1-3
- 验收：对象页可看到已挂接上下文与摘要占位
- 性质：必须先做

#### T1-5：清晰度栅栏校验器
- 内容：未满足 Goal/Boundary/Success Criteria/关键问题条件时，不允许进入计划
- 依赖：T1-3, T1-4
- 验收：系统能明确提示“为何不能进计划”
- 性质：必须先做

#### T1-6：任务列表/首页最小视图
- 内容：按状态列出 Work Item
- 依赖：T1-1
- 验收：能看到 `draft/clarifying/plan_ready`
- 性质：可并行

#### T1-7：示例数据与回归脚本
- 内容：至少 3 种输入样例（功能需求/缺陷/技术任务）
- 依赖：T1-2
- 验收：可重复验证结构化抽取质量
- 性质：可并行

### 4.1.4 本阶段验收标准
- 输入一段原始需求，可生成对象包
- 用户可修改对象包关键字段
- 可挂接基础上下文
- 不满足条件时，系统会明确阻止进入计划
- 满足条件时，Work Item 能进入 `plan_ready`

### 4.1.5 本阶段主要风险
- 风险 1：结构化抽取不稳，字段质量过差
- 风险 2：对象页字段过多，交互过重
- 风险 3：上下文接入想做太全，拖慢主线

### 4.1.6 控制策略
- 先只保证 V1 抽取可用，不追求智能极强
- 先做“可修订”，不要迷信一次抽准
- 上下文只做最小挂接，不做全量整合

## M2：计划生成与审批栅栏（预计 4~6 天）

### 4.2.1 阶段目标
让 NeoDev 真正成立“先计划、后执行”的产品承诺。

### 4.2.2 本阶段必须完成
1. Plan 对象最小可用
2. 任务拆解生成最小可用
3. 顺序/依赖表达最小可用
4. 计划审批页最小可用
5. 审批栅栏与状态流转可用

### 4.2.3 最小可用任务单元

#### T2-1：Plan 对象与版本规则
- 内容：Plan 创建、更新、替代（superseded）规则
- 依赖：M0, M1
- 验收：一个 Work Item 仅存在一个 active approved plan
- 性质：必须先做

#### T2-2：计划生成器 V1
- 内容：按对象包生成任务拆解、顺序、依赖、风险提示
- 依赖：T2-1
- 验收：样例任务能产出可读计划
- 性质：必须先做

#### T2-3：计划审批页 V1
- 内容：展示计划摘要、子任务、依赖、引用依据、审批动作
- 依赖：T2-2
- 验收：负责人可批准、退回、标记阻塞
- 性质：必须先做

#### T2-4：审批栅栏校验器
- 内容：无审批动作或高风险越界时，不能进入执行
- 依赖：T2-3
- 验收：`plan_pending_approval -> approved/executing` 有清晰拦截逻辑
- 性质：必须先做

#### T2-5：首页状态扩展
- 内容：支持 `plan_pending_approval / approved / blocked`
- 依赖：T2-3
- 验收：列表页可看出等待谁动作
- 性质：可并行

#### T2-6：计划-对象-页面映射校验
- 内容：确保 Plan 与 Goal/Boundary/Context 引用链成立
- 依赖：T2-2
- 验收：能解释“这份计划依据什么生成”
- 性质：必须先做

### 4.2.4 本阶段验收标准
- `plan_ready` 的对象可以生成计划
- 计划包含子任务、顺序、依赖
- 系统支持审批/退回/阻塞
- 未审批不得进入执行
- 边界变化时旧 Plan 可失效或被替代

### 4.2.5 本阶段主要风险
- 风险 1：任务拆解做得像普通 checklist，没有体现计划依据
- 风险 2：审批动作只是 UI 按钮，没有强约束
- 风险 3：状态流转不严，出现“未审批也在执行”

### 4.2.6 控制策略
- 计划页必须显示引用依据
- 审批必须落状态，不接受“口头通过”语义
- 执行入口严格依赖 approved 状态

## M3：执行结果页 + 证据化验收（预计 5~7 天）

### 4.3.1 阶段目标
完成 P0 第二条核心护城河：结果不是聊天回复，而是 **Artifact + Evidence + Acceptance** 的正式对象链。

### 4.3.2 本阶段必须完成
1. Artifact 对象最小可用
2. Evidence 结构最小可用
3. 执行结果页最小可用
4. 验收放行页最小可用
5. 证据栅栏与 Acceptance 状态机可用

### 4.3.3 最小可用任务单元

#### T3-1：Artifact 对象与版本规则
- 内容：执行结果对象、版本、关联 Plan
- 依赖：M2
- 验收：能区分计划内容与实际结果
- 性质：必须先做

#### T3-2：Evidence 模型 V1
- 内容：至少支持文档引用、文件变更、测试结果、预览链接四类中的两类以上
- 依赖：T3-1
- 验收：Artifact 可挂接证据项
- 性质：必须先做

#### T3-3：执行结果页 V1
- 内容：展示完成内容、未完成内容、变更范围、证据、风险、未覆盖项、评论区占位
- 依赖：T3-2
- 验收：用户能看懂“这轮到底做了什么、没做什么、依据是什么”
- 性质：必须先做

#### T3-4：验收放行页 V1
- 内容：根据 Success Criteria 生成验收清单，支持放行/补证据/退回重做/暂缓
- 依赖：T3-3
- 验收：形成 Acceptance Record
- 性质：必须先做

#### T3-5：证据栅栏校验器
- 内容：无核心证据、无风险说明、无验收清单时不可提交放行
- 依赖：T3-4
- 验收：`executing -> review_pending` 与放行动作受强约束
- 性质：必须先做

#### T3-6：返回链路完善
- 内容：验收失败后，明确区分补证据返回还是重做返回
- 依赖：T3-4
- 验收：returned_for_evidence / returned_for_rework 语义不同
- 性质：必须先做

#### T3-7：端到端 demo 脚本 V1
- 内容：从原始需求到放行的全链路脚本
- 依赖：T3-1 ~ T3-6
- 验收：可用于老板演示
- 性质：可并行

### 4.3.4 本阶段验收标准
- 执行结果成为独立 Artifact
- Artifact 附带证据与风险说明
- 可生成并执行验收清单
- 系统支持放行与退回，且有留痕
- Work Item 能进入 `released/done` 或被退回

### 4.3.5 本阶段主要风险
- 风险 1：结果页沦为“完成总结页”，证据不足
- 风险 2：验收页只勾选，不映射原始 Success Criteria
- 风险 3：退回语义混乱，导致后续闭环不清

### 4.3.6 控制策略
- 验收清单必须源自 Success Criteria
- 风险与未覆盖项必须显式展示
- 所有放行动作必须留痕可回看

# 五、任务顺序、依赖与并行策略

## 5.1 必须先做的主依赖链
严格主链如下：

`M0 骨架定盘`
→ `M1 对象包闭环`
→ `M2 计划审批闭环`
→ `M3 结果验收闭环`
→ `M4 演示与实证`

原因：
- 没有对象骨架，后续实现会失真
- 没有对象包，就无从谈计划
- 没有审批栅栏，就无法体现 NeoDev 差异
- 没有结果验收，就闭环不成立

## 5.2 可并行的任务
以下任务可与主链并行，但不得反向阻塞主链：
- 样例数据准备
- 首页最小视图
- 提示文案与空状态
- Demo 脚本撰写
- 测试用例/回归脚本
- 设计稿/原型补充
- 研究访谈材料映射

## 5.3 明确后置的任务
以下统一归为 P0+ / 后置项：
- 设计稿深度关联
- 讨论记录完整线程化
- 自动相似案例召回
- 负责人/角色建议增强
- 优先级建议增强
- 缺失上下文智能提醒增强
- 复杂组织权限/多级审批
- 经验沉淀自动化飞轮

# 六、阶段验收口径（老板视角）

## 6.1 老板看什么，不看什么
老板验收 P0 排期时，最该看的是：
1. 主闭环是否真的成立
2. 每个阶段是否都能形成可见成果
3. 风险是否被提前暴露
4. 团队是否知道哪些必须先做、哪些可以后置

不应被“看起来做了很多页面/细节”误导。

## 6.2 每个里程碑的老板验收问题

### M0 验收问题
- P0 现在到底有哪些主对象？
- 状态机和栅栏是否已经统一？
- 后续开发是否会按同一语言推进？

### M1 验收问题
- 一段模糊需求是否能稳定转为对象包？
- 关键字段能否被修订并进入 plan_ready？

### M2 验收问题
- 计划是否可解释、可审批、可拦截？
- 是否真正做到“未审批不执行”？

### M3 验收问题
- 结果是否带证据与风险？
- 是否真正做到“无证据不放行”？

### M4 验收问题
- 是否已形成稳定 demo？
- 是否诚实列出已知缺口与后续顺序？

# 七、主要风险总表

## 7.1 方向性风险
### 风险 A：P0 重新膨胀成大平台
- 表现：不停加入高级治理与增强项
- 后果：闭环迟迟无法成立
- 控制：所有新需求先判断是否服务主闭环；不服务则后置

### 风险 B：做成普通任务系统 + AI 摘要
- 表现：对象、栅栏、验收只是表面存在
- 后果：NeoDev 失去真正差异化
- 控制：每个阶段都必须检查“计划前栅栏”和“放行前栅栏”是否真实生效

## 7.2 实现风险
### 风险 C：对象模型不稳，前后端反复改
- 控制：M0 先定最小字段字典，后续只做增量

### 风险 D：状态流转失真
- 控制：把状态约束做成统一规则，不允许前端页面私自跳状态

### 风险 E：结果证据接不上真实执行产物
- 控制：M3 先接最小证据类型，不求全，但必须真能挂载

## 7.3 组织风险
### 风险 F：子智能体并行很多，但缺少统一验收面
- 控制：所有子任务都必须回到同一对象/状态/页面映射语言下验收

### 风险 G：演示视角和工程视角分离
- 控制：始终用同一条 Work Item 样例贯穿开发、测试、演示

# 八、建议的派工方式（适合继续发给子智能体）

## 8.1 推荐按 4 条子线派工

### 子线 A：对象与状态机线
负责：
- 对象字典
- 状态机规格
- 栅栏规则
- 统一接口/数据结构约束

### 子线 B：需求到计划线
负责：
- 需求输入页
- 对象页
- 结构化抽取
- 上下文挂接
- 计划生成与审批页

### 子线 C：结果到验收线
负责：
- Artifact 模型
- Evidence 模型
- 结果页
- 验收放行页
- 放行/退回记录

### 子线 D：演示与验证线
负责：
- 样例数据
- 回归脚本
- Demo 路径
- 实证脚本映射
- 验收文档与已知风险

## 8.2 派工原则
- 每个子智能体只接一个最小闭环任务包
- 每个任务包必须说明：目标、边界、输入、输出、验收、依赖
- 不允许把“做个页面”这种无边界任务直接外派

# 九、最适合先启动的前 3 个执行任务

## Top 1：输出 P0 统一对象字典 + 状态机规格
**为什么最先做：** 这是所有后续实现的公共底板，没有它，后续页面和功能实现会分叉。  
**对应任务包：** T0-1 + T0-2 + T0-3 组合任务。  
**预期产物：** 对象字段表、状态枚举、流转图、三道栅栏规则。

## Top 2：做出“需求输入页 → 可执行对象页”最小闭环
**为什么第二个做：** 这是 P0 第一个 first win，也是后续计划生成的入口。  
**对应任务包：** T1-1 + T1-2 + T1-3 + T1-5。  
**预期产物：** 输入需求后可得到 Goal/Boundary/Success Criteria/Risks/Open Questions，并能校验是否可进计划。

## Top 3：做出“计划生成 + 审批栅栏”最小闭环
**为什么第三个做：** 这是 NeoDev 与普通 AI 工具最先拉开差异的地方。  
**对应任务包：** T2-1 + T2-2 + T2-3 + T2-4。  
**预期产物：** plan_ready 对象可生成计划，未审批不能进入执行。

# 十、结尾判断

如果老大要一个严谨而现实的判断：

**NeoDev P0 当前最正确的执行策略，不是尽快铺满所有功能，而是按“对象骨架 → 对象包 → 审批计划 → 结果验收 → 演示验证”的顺序，把最小可信闭环打透。**

只要这 5 个阶段按顺序落地，NeoDev P0 就能从“方向正确”进入“产品承诺可被真实演示与验收”的状态；
如果跳过前两阶段直接堆页面或增强功能，则极容易重新掉回“功能不少，但主闭环不硬”的老问题。
