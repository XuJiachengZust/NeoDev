# 一、结论先行

## 1.1 第一批最应先启动的 3 个任务
按“最小可用单元 + 主闭环前置依赖”原则，最应先启动的不是页面堆砌，而是以下三项：

1. **任务 01：P0 统一对象字典与状态机/栅栏规格定稿**
2. **任务 02：需求输入 → 可执行对象包最小闭环定义与验收包**
3. **任务 03：计划生成 → 审批栅栏最小闭环定义与验收包**

## 1.2 为什么是这三项
原因不是它们“更抽象”，而是它们构成了真正可执行的前置骨架：
- 没有任务 01，后续页面、接口、状态、验收口径会各说各话；
- 没有任务 02，P0 没有 first win，也没有稳定的计划输入对象；
- 没有任务 03，NeoDev 就会退化成普通 AI 生成器，失去“先计划后执行”的差异化。

## 1.3 第一批任务的边界判断
本批任务 **不直接展开 M3 结果页 / 验收放行实现**，因为那是后续第二批主任务；本批目标是把 M0、M1、M2 的开工前收口做扎实，让后续开发可以真正按统一规格推进。

# 二、任务排序原则

本批排序遵循以下原则：

1. **先公共底板，后页面闭环，最后审批闭环。**
2. **先让对象成立，再让页面成立。**
3. **先让状态与栅栏可验收，再让功能开始实现。**
4. **每个任务都必须能单独交给子智能体 / 开发，并在完成后留下明确证据。**

推荐顺序：
- **顺序 1：任务 01**
- **顺序 2：任务 02**
- **顺序 3：任务 03**

其中：
- 任务 02 可在任务 01 接近定稿时并行预研，但不得跳过任务 01 的最终口径；
- 任务 03 必须建立在任务 01 完成、任务 02 产出对象包口径稳定的基础上。

## 任务 01：P0 统一对象字典与状态机 / 栅栏规格定稿

### 任务 ID
P0-BATCH1-T01

### 任务名称
统一对象字典 + 状态机 + 三道栅栏规格定稿

### 目标
把 NeoDev P0 的最小公共语言定死，形成一份可供产品、前端、后端、子智能体共用的工程基线，明确：
- Work Item / Plan / Artifact / Acceptance 等一等对象最小字段；
- Work Item、Plan、Artifact、Acceptance 的状态枚举与合法流转；
- 清晰度栅栏、审批栅栏、证据栅栏的 allow / block 条件；
- 页面与对象字段的主读写归属。

### 边界
**本任务只做规格收口，不做具体页面开发，不做数据库实现，不做 API 编码。**

明确包含：
- 对象字段最小集
- 状态机定义
- 栅栏规则
- 页面-对象映射表
- 异常/回退语义

明确不包含：
- 视觉设计稿
- 页面像素级原型
- 复杂权限 / 多级审批
- 自动相似案例召回
- 证据接入的真实工程实现

### 涉及页面 / 对象
**涉及页面：**
- 需求输入页
- 可执行对象页
- 计划审批页
- 执行结果页
- 验收放行页
- 任务列表 / 首页

**涉及对象：**
- Work Item
- Goal
- Boundary
- Context Reference
- Plan
- Task
- Artifact
- Evidence
- Risk
- Acceptance

### 预期产物
至少交付以下文档或等价结构化产物：
1. `P0_对象字典.md`
2. `P0_状态机规格.md`
3. `P0_栅栏规则清单.md`
4. `P0_页面对象映射表.md`
5. 一份汇总版 `P0_统一规格基线.md`（如果更适合一次性收口）

每份产物中必须明确：
- 字段名 / 含义 / 必填性 / 谁写谁读
- 状态迁移前置条件
- block 文案口径
- 回退路径

### 验收标准
满足以下条件才算完成：
1. 能清楚回答“每个页面读写哪些对象、哪些字段”；
2. 能清楚回答“未审批为何不能执行、无证据为何不能放行”；
3. Work Item / Plan / Artifact / Acceptance 各自状态不混淆；
4. 至少列出以下关键状态：
   - Work Item：`draft / clarifying / plan_ready / plan_pending_approval / approved / executing / review_pending / released / returned / blocked / done`
   - Plan：`draft / generated / pending_approval / approved / rejected / superseded`
   - Artifact：`in_progress / evidence_missing / submitted / under_review / accepted / returned / archived`
   - Acceptance：`not_started / checklist_ready / reviewing / approved / returned_for_evidence / returned_for_rework / waived_with_risk`
5. 三道主栅栏都具有明确 allow / block 条件：
   - 进入计划前的清晰度栅栏
   - 进入执行前的审批栅栏
   - 进入放行前的证据栅栏
6. 页面-对象映射中不存在明显“同字段多入口主写”的冲突。

### 风险
1. **过度抽象，迟迟不进入实现。**
   - 控制：只保留 P0 最小字段集，不追求一次建全。
2. **对象边界过粗，后续又回到“万能 Task”。**
   - 控制：必须坚持 Work Item / Plan / Artifact / Acceptance 拆分。
3. **状态机只是文档存在，没有真正可执行的拦截语义。**
   - 控制：每个状态都要写清楚进入条件、阻止条件、回退动作。

### 推荐顺序
**第一优先，必须最先启动并先收口。**

### 是否适合直接派工
**适合。**
可直接派给“对象与状态机线”子智能体 / 架构型开发。

### 建议派工说明
适合使用如下派工目标：
> 基于现有 PRD、功能树、页面 IA、排期文档，输出一份可供前后端直接共用的 P0 统一规格基线，包含对象字典、状态机、三道栅栏、页面-对象映射与回退规则；只做最小 P0 规格，不做实现。

## 任务 02：需求输入 → 可执行对象包最小闭环定义与验收包

### 任务 ID
P0-BATCH1-T02

### 任务名称
需求结构化闭环任务包（需求输入页 + 可执行对象页 + 清晰度栅栏）

### 目标
把 NeoDev P0 的第一段 first win 收口成可执行任务：
让用户输入原始需求后，系统能够形成一版可编辑、可校验、可推进到 `plan_ready` 的可执行对象包。

### 边界
**本任务聚焦 M1，不进入计划审批与结果验收。**

明确包含：
- 需求输入入口定义
- 结构化抽取输出定义
- 可执行对象页字段与动作定义
- 基础上下文挂接最小要求
- 清晰度栅栏校验口径
- M1 阶段验收样例与回归样例

明确不包含：
- 复杂模板体系
- 自动相似案例召回
- 多角色责任分配
- 审批动作
- Artifact / Acceptance 相关实现

### 涉及页面 / 对象
**涉及页面：**
- 任务列表 / 首页（最小状态展示）
- 需求输入页
- 可执行对象页

**涉及对象：**
- Work Item
- Goal
- Boundary
- Success Criteria
- Risks / Assumptions
- Open Questions
- Context Reference

### 预期产物
至少交付以下内容：
1. `M1_需求结构化闭环任务说明.md`
2. `M1_字段与页面交互清单.md`
3. `M1_清晰度栅栏规则.md`
4. `M1_输入输出样例包.md`（至少 3 条样例）
5. `M1_验收与回归清单.md`

若直接面向开发派工，则文档中还应补齐：
- 页面模块列表
- 每个模块的输入 / 输出 / 状态变化
- 样例数据
- 验证步骤

### 验收标准
满足以下条件才算可直接开工：
1. 明确需求输入页最小输入项：原始文本、来源类型、基础上下文挂接入口；
2. 明确结构化输出最小字段：
   - Goal
   - Boundary
   - Success Criteria
   - Risks
   - Open Questions
3. 明确可执行对象页允许的人工修订动作；
4. 明确“达到 plan_ready 的最低条件”；
5. 明确当条件不满足时，系统提示哪些 block 原因；
6. 至少提供 3 条回归样例：
   - 功能需求
   - 缺陷修复
   - 技术任务 / 技术债
7. 验收时可完成以下演示：
   - 粘贴原始需求
   - 生成对象包
   - 人工修订关键字段
   - 挂接基础上下文
   - 校验是否可进入 `plan_ready`

### 风险
1. **抽取质量不稳定，影响 first win。**
   - 控制：先接受 V1 抽取不完美，但必须支持人工修订。
2. **入口页过重，导致用户在最开始就卡住。**
   - 控制：需求输入页保持轻量，重字段集中在对象页处理。
3. **上下文挂接范围失控，拖慢主线。**
   - 控制：只保留文档、历史任务、代码范围三类最小挂接。

### 推荐顺序
**第二优先。**
必须在任务 01 基线基本明确后启动。

### 是否适合直接派工
**适合。**
可直接派给“需求到对象包”子智能体 / 产品设计 + 前端方案子线。

### 建议派工说明
> 基于 P0 统一规格，输出 M1 需求结构化闭环的直接开发任务包，覆盖需求输入页、可执行对象页、结构化字段、清晰度栅栏、样例数据与验收步骤；边界仅到 `plan_ready`，不进入计划审批和结果验收。

P0-BATCH1-T03

- 任务列表 / 首页（待审批 / 已批准 / 阻塞状态摘要）

若直接用于开发派工，文档中还应明确：
- Plan 的生成输入来自哪些对象字段；
- 计划页要展示哪些引用依据；
- 批准 / 退回 / 阻塞分别如何改状态；
- Boundary 变更后旧 Plan 如何 superseded。

### 验收标准
满足以下条件才算可直接开工：
1. 明确 `plan_ready` → `plan_pending_approval` → `approved / blocked / clarifying` 的状态路径；
2. 明确 Plan 最小输出至少包含：
   - 任务拆解
   - 执行顺序
   - 依赖关系
   - 风险提示
3. 明确计划审批页至少包含：
   - 计划总览
   - 计划依据
   - 审批意见
   - 批准 / 退回 / 阻塞动作
4. 明确“未审批不得进入执行”的 block 规则；
5. 明确当 Boundary 或关键 Success Criteria 变化时，旧 Plan 转为 `superseded`；
6. 至少提供 2 条验收样例：
   - 正常批准路径
   - 退回补充 / 阻塞路径
7. 验收时可完成以下演示：
   - 从 `plan_ready` 生成 Plan
   - 查看任务拆解与依赖
   - 执行审批动作
   - 验证未审批无法进入执行

### 风险
1. **计划生成退化成普通 checklist。**
   - 控制：计划页必须显示其依据来自 Goal / Boundary / Context。
2. **审批只是表面按钮，没有真正的状态约束。**
   - 控制：必须把 block 规则写成明确状态机条件。
3. **边界变化后旧计划仍被继续使用。**
   - 控制：补齐 superseded 规则，避免计划失真。

### 推荐顺序
**第三优先。**
必须建立在任务 01 已完成、任务 02 已明确对象包最小口径的基础上。

### 是否适合直接派工
**适合。**
可直接派给“计划与审批线”子智能体 / 产品逻辑 + 状态流转开发子线。

### 建议派工说明
> 基于 P0 统一规格和 M1 对象包口径，输出 M2 计划生成与审批闭环的直接开发任务包，覆盖 Plan 对象、计划审批页、审批状态流转、审批栅栏、样例数据与验收步骤；边界仅到进入执行前，不进入 Artifact / Acceptance。

```text
任务 01：统一对象字典与状态机/栅栏规格
   ↓
任务 02：需求输入 → 可执行对象包闭环
```

补充说明：

- 三项任务共同组成 P0 第一批“开工前收口包”，它们完成后，才适合继续把开发执行大规模派发出去。

# 六、是否已具备直接开工条件

## 6.1 结论
**结论：已具备“第一批任务包编写与分发层面”的直接开工条件，但尚未具备“大规模并行实现层面”的完全开工条件。**

## 6.2 已具备的条件
以下条件已经具备：
1. P0 方向已收敛：闭环明确为“需求结构化 → 上下文聚合 → 计划审批 → 结果评审 → 验收放行”；
2. P0 功能优先级已收敛：must / should / later 分层清楚；
3. P0 页面 IA 已具备：关键页面、页面关系、关键动作已清楚；
4. P0 主状态机已具备：Work Item / Plan / Artifact / Acceptance 已有清晰草稿；
5. P0 里程碑已具备：M0 → M1 → M2 → M3 → M4 主顺序已明确；
6. 本批前三个任务的必要性与顺序已较稳定。

## 6.3 尚未完全具备的条件
以下内容仍需先补齐或定稿，才能进入更大规模实现：
1. 统一对象字典尚未形成正式定稿版；
2. 状态机与栅栏虽有草稿，但还缺一份统一执行规格；
3. 页面-对象-字段主读写口径尚未收成单一基线文档；
4. M1、M2 的验收样例和开发任务书尚未逐项写成可直接执行版。

## 6.4 因此最诚实的判断
- **可以直接开工的，是：第一批任务包的继续细化与派发。**
- **暂不宜直接全面开工的，是：多子线同时进入具体编码实现。**

换句话说：
> 现在最合理的动作，不是直接冲代码，而是先把任务 01~03 作为第一批执行包继续落细到可派工、可验收、可回收的程度；其中任务 01 必须优先收口。
