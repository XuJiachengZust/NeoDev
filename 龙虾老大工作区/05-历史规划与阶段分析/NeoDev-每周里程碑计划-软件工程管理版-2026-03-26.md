# NeoDev 每周里程碑计划（软件工程管理版）

日期：2026-03-26  
规划周期：未来 4 周  
项目：NeoDev  
管理方式：按软件工程的里程碑、验收标准、风险控制、节奏管理来推进  
研发前提：**Codex 为开发主力，人负责需求定义、任务拆解、阶段验收、风险控制与关键决策**

---

# 一、文档目的

这份文档不是普通周计划，而是为 NeoDev 建立一套 **按周推进、按里程碑验收、按软件工程方式管理** 的执行框架。

目标有三个：

1. 把未来一个月拆成可管理、可验收、可复盘的周里程碑
2. 让 Codex 主力开发这件事能够嵌入一个稳定的工程流程
3. 避免项目进入“功能很多、推进很忙、但阶段成果不清楚”的状态

所以这份文档强调的不是“任务罗列”，而是：

- 每周目标
- 每周范围
- 每周输入输出
- 每周验收标准
- 每周风险
- 每周管理动作

---

# 二、总体项目原则

## 1. 本月总目标
本月的总目标不是做大 NeoDev，而是：

> **让 NeoDev 的产品主线更清楚、核心工作流更成熟、Codex 开发方式更工程化。**

## 2. 本月主里程碑
本月围绕三条主线推进：

### 主线 A：产品主线收敛
- 让 NeoDev 的核心价值表达更清晰
- 让版本成为主上下文之一

### 主线 B：需求文档工作流样板化
- 把需求文档工作流打磨成一个成熟样板
- 作为 NeoDev 当前最可演示、最可复用的 AI 工作流

### 主线 C：Codex 主力开发流程工程化
- 让 Codex 不只是“帮忙写代码”
- 而是嵌入到任务拆解、实现、验证、收口的工程体系中

## 3. 管理总原则

### 原则 1：每周必须有阶段性交付物
不是只说“在推进”，而是每周都要有看得见的产出。

### 原则 2：任务必须支持 Codex 高质量执行
任务应具备：
- 明确边界
- 清晰目标
- 上下文足够
- 验收标准清楚

### 原则 3：每周要做收口
不能让每周都只开新坑，必须在周末做收口、复盘、风险处理。

### 原则 4：阶段成果优先于功能数量
宁可做成一个成熟样板，也不要堆四个半成品。

# 四、Week 1：校准与建模周

## 1. 周目标
本周的目标不是大量写代码，而是：

> **把项目的方向、主线、任务组织方式、验收方式先校准。**

这是 Codex 主力开发的基础周。如果这周没打好，后面每周都会越来越乱。

## 2. 本周核心问题
本周要解决的是以下问题：

- NeoDev 本月到底主推什么？
- 产品主线如何表述？
- 哪些方向本月先不做？
- 如何把任务拆成适合 Codex 执行的形式？
- 什么叫“完成”？
- 哪些模块适合优先推进？

## 3. 本周范围

### 产品侧范围
- 明确本月产品定位
- 明确本月主线与优先级
- 明确本月样板能力
- 梳理页面 / 对象 / 版本关系

### 工程侧范围
- 建立 Codex 任务模板
- 建立最小 Definition of Done
- 建立按周管理的里程碑机制
- 梳理高风险模块与适合 agent 开发的模块

### 管理侧范围
- 确定每周例行管理动作
- 确定每周收口与复盘方式

## 4. 本周交付物

### 交付物 A：产品主线说明
至少说明：
- 本月产品一句话定位
- 本月主线
- 本月不做什么

### 交付物 B：Codex 开发任务模板
至少包含：
- 背景
- 目标
- 涉及文件
- 不可修改范围
- 验收标准
- 验证要求

### 交付物 C：最小 Definition of Done
至少包含：
- 功能完成条件
- 测试 / 验证要求
- 风险说明要求
- 必要文档要求

### 交付物 D：本月优先级列表
至少区分：
- P0：本月必须做成
- P1：本月重要推进
- P2：本月可延后

## 5. 本周验收标准
本周完成的标准不是“文档写了”，而是：

- 团队能用一句话说清 NeoDev 本月在干什么
- Codex 接任务不再依赖大量口头补充
- 后续每周任务可以按统一格式发出
- 本月工作有了清晰优先级，不再凭感觉切换

## 6. 本周风险

### 风险 1：仍然一边写一边想，方向继续漂移
应对：先完成主线与优先级文档，再大规模推进实现。

### 风险 2：Codex 开始开发，但任务依旧过大过散
应对：强制任务模板化。

### 风险 3：本周看起来“没写很多代码”，产生焦虑
应对：明确这是“打基础周”，后续效率取决于这一周质量。

## 7. 本周管理动作
- 周初：确认本月主线
- 周中：评审任务模板与 DoD
- 周末：确认 Week 2 样板工作流的具体 backlog

# 五、Week 2：样板能力周

## 1. 周目标
本周目标是：

> **把“需求文档工作流”做成 NeoDev 当前最成熟的样板能力。**

它应该成为：
- 最好演示的一条主路径
- 最适合 Codex 持续迭代的一条线
- 后续扩展其它 agent 工作流的模板

## 2. 本周核心问题
要解决的问题包括：

- 需求文档页当前最割裂、最卡手的地方是什么？
- 生成、review、diff、保存、回退这些动作是否顺畅？
- 用户能否理解现在发生了什么？
- AI 生成结果是否更可控、更可审阅？

## 3. 本周范围

### 功能范围
建议本周只聚焦需求文档工作流，不要再横向开太多功能线。

重点可包含：
- 生成前上下文呈现优化
- 生成中状态反馈优化
- review / diff 体验优化
- 保存与版本对比逻辑增强
- 子文档生成路径梳理
- 常见失败场景提示增强

### 工程范围
- 将任务拆成多条 Codex 可执行任务
- 每条任务都附带清晰验收标准
- 每个完成项都做最小验证

## 4. 本周交付物

### 交付物 A：需求文档工作流增强版
要求：
- 从进入页面到生成、审阅、保存，流程比当前明显更顺
- 用户能看懂关键状态
- 不再像多个独立功能点拼起来

### 交付物 B：样板演示路径
需要能明确演示：
- 进入某个需求
- 生成文档
- 审阅改动
- 保存版本
- 查看对比

### 交付物 C：Codex 任务样板集
沉淀一组“如何让 Codex 改 NeoDev 文档工作流”的样板任务。

## 5. 本周验收标准
- 需求文档工作流能作为本月样板能力进行演示
- 关键交互链路顺滑度明显提升
- Codex 已经可以在该模块上稳定承担多个小任务
- 团队对“如何用 Codex 改这个模块”有了可复用经验

## 6. 本周风险

### 风险 1：陷入过度打磨细节，忽视整体闭环
应对：优先保证主链路完整，而不是先卷每个边角。

### 风险 2：一口气做太多改动，导致难以验收
应对：任务继续保持小步推进。

### 风险 3：样板能力做出来了，但没有形成模板沉淀
应对：要求同步沉淀任务样板与复盘记录。

## 7. 本周管理动作
- 周初：确认样板工作流边界
- 周中：看一轮可用性与实现质量
- 周末：确认样板是否达到“可演示”标准

# 六、Week 3：闭环强化周

## 1. 周目标
本周目标是：

> **强化“版本驱动闭环”的感觉，让 NeoDev 不只是有对象和页面，而是更像一个真正组织研发过程的系统。**

## 2. 本周核心问题

- 版本是否真正成为主操作上下文？
- 用户进入版本后，能否快速看到当前状态与缺口？
- 需求、提交、文档之间是否已经体现出闭环关系？
- 系统是否开始具备“提醒你缺什么”的能力？

## 3. 本周范围

### 功能范围
重点建议包含：
- 版本页信息增强
- 版本下需求 / 提交 / 文档状态展示增强
- 缺口提示（如未归属提交、缺文档、状态不完整）
- 开始形成“下一步建议”感

### 工程范围
- 前后端围绕版本聚合信息做增强
- 避免大范围架构重构
- 以聚合接口、展示逻辑、状态提示为主

## 4. 本周交付物

### 交付物 A：版本主视角增强版
要求：
- 版本不再只是列表项
- 成为能组织工作信息的上下文容器

### 交付物 B：状态缺口提示机制（第一版）
至少具备基础提示：
- 哪些需求缺文档
- 哪些提交未归属
- 哪些状态不完整

### 交付物 C：闭环表达增强
即使没有完整自动化分析，也要开始让用户感受到：
- 系统知道“还差什么”
- 系统知道“下一步做什么”

## 5. 本周验收标准
- 版本页比当前更像主工作台，而不是数据挂点
- 用户能明显感受到 NeoDev 在组织研发闭环
- 至少一类“状态缺口”被系统清晰提示出来
- Week 2 的样板能力与版本主线开始衔接起来

## 6. 本周风险

### 风险 1：版本页堆信息，反而变乱
应对：先围绕“当前状态 / 缺口 / 下一步”组织信息。

### 风险 2：闭环表达停留在口号，功能上没有感知
应对：至少做出几个可见缺口提示点。

### 风险 3：Week 2 的样板成果没有纳入整体主线
应对：要求版本视角和文档工作流形成连接。

## 7. 本周管理动作
- 周初：确认版本主视角要展示的最小信息集合
- 周中：看版本页是否过载
- 周末：确认闭环感是否可被讲述

# 七、Week 4：收口与发布周

## 1. 周目标
本周目标是：

> **把这个月的成果收成一个阶段版本，能讲清楚、能复盘、能为下个月继续滚动。**

## 2. 本周核心问题

- 哪些成果已经足够作为阶段结论？
- 哪些问题必须在月底前修掉？
- 哪些遗留要明确进入下个月？
- 这个月形成了哪些可复用的 Codex 开发经验？

## 3. 本周范围

### 产品范围
- 收口关键体验问题
- 统一术语和表达
- 整理阶段成果

### 工程范围
- 修关键缺陷
- 清理明显脏点
- 补必要文档
- 整理遗留 backlog

### 管理范围
- 输出月度总结
- 输出下月路线图输入
- 输出 Codex 使用经验总结

## 4. 本周交付物

### 交付物 A：本月阶段总结
至少包括：
- 本月达成项
- 未达成项
- 关键经验
- 关键风险

### 交付物 B：下月路线图输入
至少包括：
- 建议继续推进的主线
- 技术债优先级
- 继续适合 Codex 推进的任务类型

### 交付物 C：Codex 协作经验总结（V1）
至少包括：
- 什么类型任务最适合 Codex
- 常见跑偏点
- 有效任务模板
- 有效验收方式

## 5. 本周验收标准
- 月度成果可以被清晰讲述
- 关键样板与主线已初步成立
- 团队对下个月怎么继续有明确输入
- Codex 开发经验开始被文档化，而不是只存在对话里

## 6. 本周风险

### 风险 1：最后一周继续开新坑，导致收不住
应对：严格限制 Week 4 新增范围。

### 风险 2：成果很多但讲不清
应对：先整理“一个月最重要的三件成果”。

### 风险 3：经验没有沉淀，导致下月重复踩坑
应对：强制输出协作经验文档。

## 7. 本周管理动作
- 周初：冻结新增范围
- 周中：看关键瑕疵修复情况
- 周末：做阶段复盘与下月计划输入

# 八、建议的周会 / 管理节奏

为了让这套里程碑真正运转，建议每周固定三类管理动作：

## 1. 周启动（Monday Kickoff）
关注：
- 本周目标
- 本周范围
- 本周 P0 任务
- Codex 任务拆解是否完成

## 2. 周中检查（Midweek Check）
关注：
- 是否跑偏
- 验收标准是否仍成立
- 风险是否扩大
- 是否需要缩范围

## 3. 周收口（Friday Wrap-up）
关注：
- 本周已交付内容
- 未完成内容处理方式
- 关键问题与经验
- 下周输入是否清楚

# 十、最终建议

如果这一个月你真的要用“软件工程 + Codex 主力”的方式管理 NeoDev，我最建议坚持三件事：

## 1. 不要每周都像从零开始
每周必须围绕里程碑，而不是围绕临时灵感推进。

## 2. 不要让 Codex 直接吞大而模糊的任务
要先做人类拆解，再让 Codex 执行。

## 3. 不要只记“做了什么”，要记“达到什么阶段”
软件工程里的管理重点不是忙不忙，而是：
- 是否达成里程碑
- 是否通过验收
- 是否降低了项目不确定性
