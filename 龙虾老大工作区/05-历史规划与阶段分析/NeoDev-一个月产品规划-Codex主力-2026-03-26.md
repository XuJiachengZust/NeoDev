# NeoDev 一个月产品规划（Codex 主力开发版）

日期：2026-03-26  
适用周期：未来 4 周  
项目：NeoDev  
研发前提：**开发主力为 Codex，人工负责方向、拆解、验收与关键决策**

---

## 一、规划目标

这份规划不是泛泛的“愿景稿”，而是围绕 **未来一个月** 的真实落地来写，目标是解决三个问题：

1. **产品主线要收拢**：NeoDev 当前能力不少，但主线还不够锋利。
2. **开发节奏要适配 Codex**：既然主力开发是 Codex，就不能按传统“人脑里装所有上下文”的方式推进，而要按可拆解、可验证、可复用的方式组织工作。
3. **一个月内要交付可感知进展**：不能只是继续堆功能，要在产品层、工程层、AI 工作流层都产出肉眼可见的提升。

所以本月目标不是“做更多”，而是：

> **收敛 NeoDev 主线，让产品更像一个真正可持续演进的 AI 原生研发平台，并建立适合 Codex 持续开发的推进方式。**

---

## 二、一个月后的理想状态

如果这个月执行得好，到月底时 NeoDev 应该达到下面的状态：

### 产品层
- 用户能明确理解 NeoDev 的主价值：
  - 围绕 **产品 / 版本 / 需求 / 提交 / 文档 / Agent** 的研发闭环
- 关键主入口更清晰
- 至少形成一个真正可讲、可演示、可持续推进的主工作流

### 交互层
- 首页 / Dashboard / 版本视图不再只是信息散列，而开始体现“下一步该做什么”
- 需求文档工作流更完整，体验更顺
- 产品对象之间关系更清晰，不容易迷路

### 工程层
- NeoDev 的开发方式开始适配 Codex
- 任务粒度、文档、验证方式更利于 agent 开发
- 至少形成一套可持续复用的“Codex 开发工作法”

### AI / Agent 层
- AI 不再只是一些零散按钮，而开始进入明确工作流
- 至少有一条 agent 工作流明显成熟（建议是需求文档工作流）

---

## 三、本月总策略：做减法，不做散

这个月不建议横向开太多线。最重要的是：

### 核心原则 1：先收主线，再扩功能
当前 NeoDev 最大问题不是“功能少”，而是“主线还不够聚焦”。

### 核心原则 2：优先做对外可解释、对内可复用的能力
这个月每一项工作都尽量满足两个要求：
- 对外能讲清价值
- 对内能成为后续开发基础

### 核心原则 3：按 Codex 友好方式组织开发
既然主力是 Codex，那么任务必须：
- 边界清晰
- 目标明确
- 上下文足够
- 验收标准清楚
- 尽量不要“超大模糊任务”

### 核心原则 4：做一个“样板闭环”比同时做五个半成品更值钱
本月应该优先把一条线做透，而不是多个方向都点一下。

---

## 四、一个月主线建议

### 主线 A：版本驱动的产品闭环（产品主叙事）
这是对外的主叙事。

建议你这个月明确：

> **NeoDev 的核心不是泛 AI 平台，而是围绕“版本”组织需求、代码、文档与协作。**

这条主线会成为：
- 页面组织依据
- 功能优先级依据
- 后续产品故事依据

### 主线 B：需求文档工作流（本月重点样板）
这是最适合一个月内打透的 agent/AI 工作流。

因为它已经有基础：
- RequirementDocPage 已经较完整
- 有生成 / diff / review / 预生成对话 / 子文档思路
- 很适合成为“NeoDev 的代表性能力”

### 主线 C：Codex 驱动开发体系（研发方法主线）
既然开发主力是 Codex，那这个月必须同步建立一套 **适合 Codex 的开发节奏**，否则后面越做越乱。

# 角度一：产品定位与叙事

## 本月目标
让 NeoDev 的产品定位从“能力很多”变成“主线清楚”。

## 本月要完成的事情

### 1. 明确一句对外定位
建议本月内部先统一成：

> **NeoDev = 面向研发团队的 AI 原生需求—版本—代码闭环平台**

这句未必是最终 marketing slogan，但足够指导本月所有设计与开发决策。

### 2. 明确产品主对象优先级
建议当前阶段按以下优先级理解产品：

1. 产品（Product）
2. 版本（Version）
3. 需求（Requirement）
4. 提交（Commit）
5. 文档（Doc）
6. Agent（作为工作流能力，而不是独立产品中心）

### 3. 明确本月不做什么
本月建议暂时不优先：
- 继续横向扩一堆新 AI 功能入口
- 追求过于宏大的企业级权限体系
- 把注意力放在炫技式图谱展示上
- 做太多与主线弱相关的新页面

## 本月产出
- 一页产品定位说明
- 一版对象优先级说明
- 一版当前阶段“做 / 不做”清单

---

# 角度二：产品体验与信息架构

## 本月目标
让用户进入系统后，不再只看到“有很多页面”，而是知道自己下一步该做什么。

## 本月重点方向

### 1. 强化主入口
建议本月重点梳理以下主路径：

- 进入产品
- 选择版本
- 查看当前版本状态
- 管理需求
- 生成 / 完善需求文档
- 查看提交与影响分析

### 2. 收敛页面关系
建议逐步形成“以产品为总容器，以版本为主操作上下文”的结构感。

### 3. 建议本月重点优化两个界面

#### 界面 A：产品 Dashboard / 版本入口
要让它回答几个关键问题：
- 当前最重要的版本是什么？
- 当前版本进展如何？
- 还缺什么？
- 下一步应该做什么？

#### 界面 B：需求文档页
要让它成为 NeoDev 最成熟的一页：
- 上下文更明确
- 生成更可控
- review 更顺畅
- diff 更可理解
- “文档不是孤立文本，而是版本研发过程的一部分”

## 本月产出
- 一版主流程信息架构图
- 一版 Dashboard 改造思路
- 一版需求文档页增强方案

---

# 角度三：功能规划

## 本月功能优先级
我建议只抓三组：

### P0：需求文档工作流增强
目标：把它做成样板能力。

建议优先补：
- 生成前上下文显示更清楚
- 生成后质量提示 / 缺失项提示
- review 流程更稳定
- 保存、版本对比、回退逻辑更顺
- 子级文档生成流程更清晰

### P1：版本视角增强
目标：让版本真正成为中枢，而不只是一个附属对象。

建议优先补：
- 版本概览信息更完整
- 版本下需求 / 提交 / 文档状态更可见
- 版本成为导航和决策中心

### P1：未归属提交 / 缺口提示
目标：开始体现“闭环系统”的价值。

建议优先补：
- 哪些提交还没归属需求
- 哪些需求还没文档
- 哪些版本存在明显缺口

### P2：报告化能力雏形
目标：让系统开始具备管理者视角。

建议优先补：
- 简单版本周报 / 状态总结
- 风险提示
- 下一步建议

# 角度四：AI / Agent 工作流

## 本月目标
不是增加更多 AI 按钮，而是让已有 AI 能力更像“流程能力”。

## 本月重点策略

### 1. 确立一个样板 agent 工作流
推荐就选：**需求文档工作流**

原因：
- 已有基础最好
- 用户价值最直观
- 容易展示“NeoDev 的 AI 不是闲聊，而是工作流”

### 2. 让 AI 输出更可控
本月优先做：
- 输入上下文更明确
- 输出格式更稳定
- review / diff 更自然
- 错误提示更明确

### 3. 开始建立 agent 质量感知
即使本月不做非常复杂的评分系统，也建议开始加：
- 生成成功 / 失败状态
- 常见错误记录
- 明确的用户可见反馈

---

# 角度五：研发方式（Codex 主力开发）

## 本月目标
让开发方式从“人脑硬带 AI”升级到“人主导、Codex 持续稳定输出”。

## 关键现实
如果主力是 Codex，那你这个月必须同时建设：
- 任务拆解方式
- 仓库上下文
- 验收方式
- 复盘沉淀

否则开发会越来越依赖临场解释，越做越散。

## 本月建议建立的机制

### 1. 任务模板化
以后发给 Codex 的任务，尽量统一包含：
- 背景
- 目标
- 涉及文件
- 不要动什么
- 验收标准
- 要跑什么验证

### 2. 一次只让 Codex吃一个清晰任务
避免：
- “把整个版本系统优化一下”
- “把需求模块升级一下”

推荐：
- “在某页增加某状态块”
- “给某 service 增加一个计算函数和测试”
- “把某组件拆分成 hook + presentational component”

### 3. 开发流程建议
建议本月开始采用：

- 小任务：Codex 直接改 + 自测 + 人审
- 中任务：Codex 先方案，确认后再改
- 大任务：先拆成 3~5 个小任务，分别推进

### 4. 结果回收
每次 Codex 完成后，必须回答：
- 改了什么
- 风险是什么
- 哪些地方没覆盖
- 跑了哪些验证

---

# 角度六：工程质量与节奏管理

## 本月目标
控制熵增，避免因为 agent 加速导致代码库快速变乱。

## 本月重点

### 1. 先建立“Definition of Done”
本月非常建议形成一版最小 DoD：
- 功能完成
- 相关测试通过
- 不破坏现有主流程
- 命名与结构符合当前风格
- 有必要说明时补文档

### 2. 控制无效修改
主力是 Codex 时，一个风险是它会做很多“顺手优化”。
所以要明确：
- 不要顺手大改无关代码
- 不要无边界重命名
- 不要混进太多风格调整

### 3. 每周做一次收口
建议每周固定做一次：
- 本周功能收口
- 文档更新
- 技术债记录
- 下一周任务重排

# 角度七：管理与节奏

## 这个月建议的节奏

### 第 1 周：校准周
目标：把方向和打法校准。

重点：
- 明确本月产品主线
- 梳理 Codex 开发方法
- 定义本月 P0 / P1 / P2
- 定义需求文档工作流增强目标
- 明确 Dashboard / 版本主入口改造方向

### 第 2 周：样板周
目标：做出一个可感知的样板能力。

重点：
- 集中打磨需求文档工作流
- 补关键体验缺口
- 提升 AI 生成 + review 的稳定性
- 做出一条清晰的演示路径

### 第 3 周：闭环周
目标：把版本、需求、文档、提交之间的关系拉得更紧。

重点：
- 强化版本视角
- 增加缺口提示 / 未归属提交提示
- 让系统开始体现“闭环”的味道

### 第 4 周：收口与可讲述周
目标：让这个月的成果能讲清楚、能继续滚动。

重点：
- 整理成果
- 统一术语与主叙事
- 修关键瑕疵
- 形成下个月路线图

#### 研发任务

- 建立最小 Definition of Done

#### 预期成果
- 本月主线清晰
- 开发方式可复制
- 不再靠临时口述推动全部开发

### Week 2：打磨需求文档样板工作流

#### 产品任务
- 优化需求文档页关键流程
- 梳理生成、review、diff 的用户路径
- 增加更明确的状态反馈

#### 研发任务
- 拆成多个小任务交给 Codex
- 强制每个任务做最小验证
- 积累一套可复用的 prompt / task 模板

#### 预期成果
- 需求文档工作流可作为演示样板
- Codex 开发节奏开始稳定

### Week 3：强化版本主线与闭环提示

#### 产品任务
- 强化版本视角页面
- 增加缺口提示 / 状态提示
- 让“版本”从数据容器变成操作上下文

#### 研发任务
- 增加小步迭代任务
- 聚焦页面信息组织和后端聚合接口
- 避免大范围重构

#### 预期成果

### Week 4：收口、整理、准备下月

- 统一产品叙事

#### 研发任务
- 修关键瑕疵
- 补必要文档
- 清理明显技术债
- 输出下月 backlog

#### 预期成果
- 这个月不是“做了一堆零碎”，而是形成一个有方向的阶段成果

## 七、这个月最值得盯住的 5 个指标

建议不要上来就搞复杂指标系统，本月先盯这 5 个：

1. **主流程清晰度**
   - 新人是否能看懂主路径
2. **需求文档工作流完成度**
   - 是否已成为稳定样板
3. **版本视角可用性**
   - 版本是否真正成为主操作上下文
4. **Codex 开发稳定性**
   - 任务是否越来越容易拆、越来越少跑偏
5. **月末可讲述性**
   - 这个月成果能否被一句话讲清楚

## 八、关键风险与规避建议

### 风险 1：想做太多
规避：只抓 1 条样板线 + 1 条主叙事线 + 1 套 Codex 开发方式。

### 风险 2：Codex 开发越来越快，但越来越乱
规避：强制小任务、明确验收、每周收口。

### 风险 3：继续堆功能，主线反而更散
规避：每做一个功能先问一句：它是否强化“版本驱动闭环”？

### 风险 4：AI 功能很多，但没有代表作
规避：本月优先把需求文档工作流做成代表作。

如果只允许我给一句最重要的建议，那就是：

如果只允许我给一句关于研发的建议，那就是：

> **既然主力是 Codex，就把任务拆解、上下文、验证和收口机制先建立起来，否则越往后越难控。**
