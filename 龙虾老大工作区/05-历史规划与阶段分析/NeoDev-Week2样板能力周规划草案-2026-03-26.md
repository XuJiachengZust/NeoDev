## 1. 规划结论先说

Week1 已经基本完成“校准与建模”主任务，NeoDev 目前已经具备进入 Week2 的条件。下一阶段不建议再横向开新大线，而应按既定样板能力周思路，集中打磨 **需求文档工作流**，把它从“已有很多能力点”推进到“可稳定演示、可持续迭代、可沉淀方法论”的阶段成果。

**本阶段建议主题：**

> **Week2 = 需求文档工作流样板能力周**  
> 目标不是再堆新功能，而是把“进入需求 → 生成文档 → 审阅改动 → 保存版本 → 查看差异/子文档”的主链路打磨成一个可讲、可演示、可验收的样板闭环。

## 3. Week2 总目标

### 3.1 阶段目标

在 1 周内，把 NeoDev 的需求文档工作流做成当前最成熟、最可演示的一条主路径。

### 3.2 具体目标

1. **主链路可用**：用户能顺畅完成“查看需求 → 生成/编辑文档 → 审阅 → 保存 → 看版本差异”。
2. **状态可理解**：生成中、失败、完成、待审阅、已保存等关键状态清楚可见。
3. **结果可审阅**：不是只有 AI 输出，而是有明确 review/diff 入口与接受机制。
4. **演示可讲述**：能整理成一条固定演示路径，给老大或他人看时不再依赖大量口头解释。
5. **工程可复用**：把 Week2 的任务拆解、验收方式沉淀成后续能力周的样板方法。

## 4. Week2 范围

### 4.1 本阶段纳入范围

#### A. 需求文档主链路体验
- 需求文档页面主流程梳理
- 生成前提示/上下文展示优化
- 生成中状态反馈优化
- 生成后待审阅与保存动作梳理
- 文档版本列表、diff、review 入口清晰化

#### B. 关键失败路径治理
- 生成失败的提示与恢复动作
- 无文档、无上下文、生成中断等异常场景提示
- 子文档生成前置条件提示优化

#### C. 可演示样板整理
- 固定一条演示路径
- 明确 demo 数据或 demo 场景
- 输出样板能力验收清单

#### D. 工程化配套
- Week2 任务包拆成多个最小可用单元
- 每个任务有验收标准与验证命令
- 每个完成项可独立 review / 提交

### 4.2 明确不纳入范围

本阶段 **不建议** 纳入以下事项：

1. 不做 Deep Agents 架构重写
2. 不做新的解析语言扩展
3. 不做全站 UI 重设计
4. 不做跨多个业务域的大型数据库重构
5. 不把 Week2 扩大成“所有页面都优化”
6. 不把版本主线增强、状态缺口提示的大范围工作提前并入（那更适合 Week3）

#### W2-P0-04 样板演示路径落地

## 8. 风险清单

### 风险 R1：Week2 范围失控，重新变成“大而散”
**说明：** 一旦把文档工作流之外的版本页、全站状态提示、更多页面改造都卷进来，Week2 会再次失焦。  
**应对：** 强制限定在需求文档主链路；非主链路项放入 Week3 候选池。

### 风险 R2：陷入细节打磨，闭环反而没成
**说明：** 很容易一直改按钮、文案、局部 UI，但没有把主路径真正走顺。  
**应对：** 优先完成“可走通、可审阅、可保存、可演示”的主闭环，再做细节优化。

### 风险 R3：现有能力很多，但状态语义仍混乱
**说明：** 现在已有生成、diff、review、children docs 等能力，但若状态提示混乱，用户感知仍会很差。  
**应对：** 把“状态语义清楚”列为 P0，而不是当成附带优化。

### 风险 R4：任务切分不当，导致 Codex 持续跨边界改动
**说明：** 若一个任务同时包含页面重构、接口设计、流程改造、文档整理，容易超出最小提交单元。  
**应对：** 严格按主链路节点拆任务，每个任务只解决一个最小问题。

### 风险 R5：Week2 做完后仍缺少“给老大看的成果包”
**说明：** 只改代码但没有演示路径、验收清单、风险说明，阶段价值难以被确认。  
**应对：** 把“样板演示脚本 + 验收清单 + 风险清单”列入正式交付物。

## 9. 验收标准

### 9.1 阶段验收（Week2 Done）

Week2 完成不以“提交数”判断，而以以下条件判断：

1. **样板主链路可演示**
   - 能从某个需求进入文档页
   - 能触发生成或看到已有生成结果
   - 能进行 review / diff
   - 能保存并查看版本结果

2. **关键状态可理解**
   - 生成中、已完成、失败、待审阅等状态明确
   - 用户知道下一步能做什么

3. **异常场景有基本可用反馈**
   - 至少覆盖无文档、生成失败、前置条件不足等典型问题

4. **工程结果可审核**
   - 每个任务具备最小验证
   - 关键改动通过对应测试 / build / 手工链路验证
   - 结果可以套用 `docs/REVIEW_GATE.md` 审核

5. **形成样板沉淀**
   - 至少有一份演示路径说明
   - 至少有一份验收清单
   - 至少有一份已知风险/遗留说明

### 9.2 最小验证建议

- 后端改动：跑对应 `pytest` 目标文件
- 前端交互改动：`cd web && npm run test:run`
- 涉及构建路径：`cd web && npm run build`
- 主链路验收：补一轮手工演示记录或截图/步骤记录

## 11. 对老大的建议决策点

当前最值得老大决策/确认的，不是细节 UI，而是下面 3 个方向点：

### 决策点 D1：Week2 是否完全聚焦需求文档工作流
建议：**是。**  
理由：当前仓库已经具备这条链路的能力底座，最适合做成一个阶段样板；如果此时再横向开线，成果会重新变散。

### 决策点 D2：Week2 的阶段成功标准，是否以“可演示闭环”优先于“功能数量”
建议：**是。**  
理由：NeoDev 当前更需要一个成熟样板，而不是更多半成品点位。

### 决策点 D3：Week2 完成后，Week3 是否按“版本主线 + 状态缺口提示”推进
建议：**是。**  
理由：这与已有月度里程碑文档一致，也能自然承接 Week2 的样板成果。

## 12. 最终建议

从工程节奏看，Week1 已经把“怎么推进”搭起来了；Week2 应该开始回答“NeoDev 当前最能打的一条能力链是什么”。

我的判断是：

> **需求文档工作流就是 NeoDev 目前最适合被打磨成样板能力的一条主线。**

因此，下一阶段最优策略不是继续四处补点，而是：

- 收敛范围
- 锁定主链路
- 以样板闭环为验收标准
- 以演示能力为阶段成果
- 以文档化沉淀保证后续可复制

这样 Week2 结束时，老大看到的就不只是“一堆提交”，而是一个可以明确评估价值的阶段样板。
