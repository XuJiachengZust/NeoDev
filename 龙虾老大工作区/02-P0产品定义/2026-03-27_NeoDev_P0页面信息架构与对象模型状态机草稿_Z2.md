# 一、本文目标

本文继续把 NeoDev 的 P0 下钻到两个产品与研发可以直接共读的层面：

1. **P0 页面/信息架构**：明确最小闭环应该有哪些页面、页面之间如何跳转、每页的核心信息与关键动作是什么。  
2. **P0 对象模型与状态机**：明确系统中真正的一等对象、对象关系、状态流转、拦截栅栏与放行机制是什么。

本文坚持一个核心原则：

> NeoDev 的 P0 不是做“又一个 AI 工作台”，而是把 **需求 → 计划 → 执行 → 证据 → 验收放行** 变成一条真正可追踪、可审查、可放行的对象化链路。

---

# 二、P0 闭环总图

## 2.1 P0 最小闭环

```text
原始需求输入
  ↓
结构化对象包（Goal / Boundary / Success Criteria / Risks / Open Questions）
  ↓
上下文聚合（文档 / 历史任务 / 模块 / 讨论）
  ↓
计划生成与审批（Plan / Task Breakdown / Approval Gate）
  ↓
执行产物（Artifact）
  ↓
证据化评审（Evidence / Risk / Coverage）
  ↓
验收放行（Acceptance / Approve / Return）
```

## 2.2 P0 关键产品判断

P0 不追求“一上来覆盖全部研发管理”，而是优先拿下两个关键节点：

1. **执行前的计划栅栏**：没有目标、边界、待确认项和审批，不进入执行。  
2. **执行后的放行栅栏**：没有证据、风险说明、未覆盖项和验收记录，不宣称完成。

这两个栅栏共同支撑 NeoDev 的核心承诺：
- **先计划**
- **带边界**
- **有证据**
- **可放行**

# 三、P0 页面/信息架构

## 3.1 页面架构总览

建议 P0 收敛为 6 个主页面/主视图：

1. **需求输入页**
2. **可执行对象页**
3. **计划审批页**
4. **执行结果页（Artifact Page）**
5. **验收放行页**
6. **任务列表 / 首页总览页**

其中 1-5 构成主闭环，6 负责列表化进入与状态可视化。

## 3.2 页面关系图

```text
[任务列表/首页]
   ├─ 新建 → [需求输入页]
   ├─ 点击草稿/待确认对象 → [可执行对象页]
   ├─ 点击待审批对象 → [计划审批页]
   ├─ 点击执行中/待验收对象 → [执行结果页]
   └─ 点击待放行对象 → [验收放行页]

[需求输入页]
   ↓ 生成对象包
[可执行对象页]
   ↓ 上下文补全 / 人工修订 / 满足栅栏
[计划审批页]
   ↓ 批准后进入执行
[执行结果页]
   ↓ 证据齐备后提交验收
[验收放行页]
   ├─ 放行 → 任务完成
   └─ 退回 → 回到可执行对象页或执行结果页
```

---

## 3.3 页面 1：任务列表 / 首页总览页

### 页面定位
P0 的统一入口页，不承担复杂管理职责，只解决三件事：
- 我现在有哪些对象在推进；
- 每个对象处于什么状态；
- 我应该先看哪个。

### 核心模块
1. **按状态分组的对象列表**
   - 草稿
   - 待确认
   - 待审批
   - 执行中
   - 待验收
   - 已放行
   - 已退回
2. **每个对象的状态摘要卡**
   - 标题
   - 当前 Goal 摘要
   - 当前状态
   - 当前阻塞/待确认项数量
   - 最近更新时间
   - 当前责任动作（如“待审批”“待补证据”“待放行”）
3. **新建任务入口**
4. **高风险/高优先对象提示**

### 关键动作
- 新建需求
- 进入对象详情
- 过滤“需要我处理”的对象
- 识别是否存在卡在待确认/待验收的对象

### 为什么需要这个页面
P0 虽然强调闭环，但没有总览页，用户仍然要靠聊天和记忆判断“现在走到哪了”。
首页的价值不是 PM 看板，而是**状态驱动导航**。

---

## 3.4 页面 2：需求输入页

### 页面定位
把原始需求、会议结论、聊天摘要、PRD 等输入材料变成 NeoDev 的正式起点。

### 核心模块
1. **原始输入区**
   - 粘贴文本
   - 上传/关联文档
   - 标注任务类型（功能/缺陷/技术债/探索）
2. **输入来源区**
   - 文档链接
   - 历史任务链接
   - 模块/仓库范围
   - 设计稿/原型链接
3. **系统预解析区**
   - 自动识别目标候选
   - 自动识别边界候选
   - 自动识别风险/未知项候选
4. **生成按钮：可执行对象包**

### 关键动作
- 输入原始需求
- 挂接初始上下文
- 触发结构化生成

### 产出
从这里进入后，系统创建一个 **Work Item（工作项）**，并生成初版：
- Goal
- Boundary
- Success Criteria Draft
- Risks
- Open Questions

### 页面原则
该页必须足够轻，不要在入口页就把所有字段展开成重型表单。  
入口的关键不是“填写完整”，而是“足够快地进入结构化对象页”。

---

## 3.5 页面 3：可执行对象页

### 页面定位
这是 P0 最核心的对象页。它负责把“看起来像需求的东西”变成“真正可计划的对象”。

### 页面结构

#### A. 顶部摘要区
- 任务标题
- 当前状态（草稿 / 待确认 / 可计划）
- Goal 摘要
- Boundary 摘要
- 风险等级
- 当前是否满足进入计划阶段的条件

#### B. 结构化对象区
- Goal
- Boundary
- Success Criteria
- Risks / Assumptions
- Open Questions

#### C. 上下文区
- 关联文档
- 历史任务
- 相关模块/代码范围
- 设计/原型
- 讨论结论
- 上下文摘要卡片

#### D. 缺失提醒区
- 缺少代码范围
- 缺少验收依据
- 有关键待确认项未解决

#### E. 下一步动作区
- 继续补上下文
- 人工修订对象包
- 提交进入计划生成

### 关键动作
- 修订 Goal / Boundary / Success Criteria
- 确认或补全 Open Questions
- 补齐上下文
- 提交进入计划阶段

### 这个页面的本质
它不是“需求详情页”，而是 **计划前栅栏页**。  
只要这里还存在关键不确定性，系统就不应允许用户把任务当成“已经开始执行”。

---

## 3.6 页面 4：计划审批页

### 页面定位
把对象页中的“可计划对象”转换成“已批准执行对象”。

### 页面结构

#### A. 计划总览区
- Plan 摘要
- 任务拆解（父任务 / 子任务）
- 执行顺序
- 依赖关系
- 角色建议
- 优先级建议

#### B. 计划依据区
- 本计划引用了哪些 Goal / Boundary / Context
- 哪些不确定项已解决
- 哪些仍是显式风险但可以接受

#### C. 审批意见区
- 审批人意见
- 修改要求
- 附加限制条件

#### D. 审批动作区
- 批准进入执行
- 退回继续补充
- 标记阻塞

### 关键动作
- 审阅任务拆解与依赖
- 判断计划是否越界
- 正式批准 / 退回

### 页面价值
这是 NeoDev “先计划再执行”最明确的产品化承诺。  
很多系统只有任务创建，没有“计划批准”这个栅栏；NeoDev 的差异恰恰在这里。

---

## 3.7 页面 5：执行结果页（Artifact Page）

### 页面定位
该页是执行输出的统一对象，承接 AI 或人完成的一轮执行结果。

### 页面结构

#### A. 结果摘要区
- 对应哪个 Work Item / Plan
- 本轮执行目标
- 本轮完成内容
- 本轮未完成内容
- 本轮变更范围
- 当前状态（执行中 / 待验收 / 已退回）

#### B. 证据面板
- 引用文档
- 代码 diff / 文件变更
- 测试结果 / 验证记录
- Demo / 预览链接
- 相关评论/讨论

#### C. 风险与未覆盖项区
- 已知风险
- 未覆盖边界
- 需人工复核点
- 建议后续动作

#### D. 评论线程区
- 面向本结果页的评论
- 指向具体证据或结果项的批注

#### E. 提交验收区
- 生成验收清单
- 提交进入验收放行

### 关键动作
- 查看本轮到底做了什么
- 查看证据是否足够支撑验收
- 识别哪些地方没做/不能放行
- 提交给负责人验收

### 为什么这页是一等页面
NeoDev 不能把“AI 回复内容”当结果；真正的结果应该是一个可审查对象。  
Artifact Page 是 P0 与普通 AI 聊天式工具最拉开差距的地方。

---

## 3.8 页面 6：验收放行页

### 页面定位
把“看过结果”升级为“基于证据的正式放行动作”。

### 页面结构

#### A. 验收依据区
- 原始 Success Criteria
- 当前验收清单
- 对应证据映射

#### B. 放行检查区
- 每个验收项的通过/不通过/待补充
- 风险接受声明
- 未覆盖项确认

#### C. 最终动作区
- 放行
- 退回补充证据
- 退回重做
- 暂缓决定

#### D. 记录区
- 谁放行
- 何时放行
- 基于哪些证据放行
- 退回原因是什么

### 关键动作
- 逐项勾验收清单
- 决定是否放行
- 留下审查记录

### 页面价值
它把“负责人背锅式口头 OK”变成“有证据、有记录、有边界说明的正式决策”。

# 四、页面之间的核心导航与对象穿透

## 4.1 页面跳转原则

### 原则 1：始终围绕同一个 Work Item 导航
不是从功能模块跳模块，而是从同一个工作对象穿透不同阶段。

### 原则 2：每个页面都要有“当前状态摘要”
用户不应依赖回忆判断“现在到哪一步了”。

### 原则 3：每个页面都要暴露“下一关键动作”
避免对象停留在半成品状态却没人知道下一步。

## 4.2 对象穿透示例

```text
需求输入页：创建 Work Item
  ↓
可执行对象页：补全 Goal / Boundary / Context
  ↓
计划审批页：形成并批准 Plan
  ↓
执行结果页：生成 Artifact + Evidence
  ↓
验收放行页：生成 Acceptance Record
  ↓
任务列表页：状态变为已放行/已完成
```

# 五、P0 对象模型

## 5.1 P0 一等对象建议

P0 不应只建“任务”一个大对象，而应至少显式建模以下对象：

1. **Work Item**：本次工作的主对象/容器对象
2. **Goal**：为什么做、要达成什么
3. **Boundary**：做什么、不做什么、不能突破什么
4. **Context Reference**：与本工作相关的文档、任务、代码、设计、讨论
5. **Plan**：如何做、拆成哪些步骤、依赖关系是什么
6. **Task**：Plan 下的执行单元
7. **Artifact**：某一轮实际执行输出
8. **Evidence**：支撑 Artifact 可审查的证据
9. **Risk**：风险、假设、未覆盖项
10. **Acceptance**：验收清单与放行记录

---

## 5.2 对象关系图

```text
Work Item
 ├─ has one Goal
 ├─ has one Boundary
 ├─ has many Context References
 ├─ has zero or one active Plan
 ├─ has many Tasks
 ├─ has many Artifacts
 ├─ has many Risks
 └─ has one or more Acceptance Records

Plan
 ├─ belongs to one Work Item
 ├─ generates many Tasks
 └─ is approved/rejected before execution

Artifact
 ├─ belongs to one Work Item
 ├─ may reference one Plan version
 ├─ has many Evidence items
 ├─ has many Risk items
 └─ enters Acceptance flow

Acceptance
 ├─ belongs to one Artifact (or artifact version)
 ├─ checks against Success Criteria
 └─ records approve / return / hold
```

---

## 5.3 为什么这样拆，而不是只用一个 Task 对象

如果把所有内容都塞进一个“任务详情页”，会出现几个问题：

1. **目标和边界被埋没**：容易退化回传统 issue。  
2. **计划与结果混在一起**：用户难以分清“计划如此”还是“实际如此”。  
3. **证据和验收变成附件**：而不是主路径。  
4. **无法形成强状态机**：因为一个对象同时承载太多阶段语义。

因此更合理的建模方式是：
- 用 **Work Item** 作为主对象；
- 用 **Plan / Artifact / Acceptance** 作为阶段性子对象；
- 用 **Goal / Boundary / Evidence / Risk** 作为强约束信息对象。

# 六、P0 状态机设计

## 6.1 主状态机：Work Item 状态机

建议 Work Item 采用以下主状态：

1. `draft`（草稿）
2. `clarifying`（待确认）
3. `plan_ready`（可计划）
4. `plan_pending_approval`（计划待审批）
5. `approved`（计划已批准）
6. `executing`（执行中）
7. `review_pending`（待验收）
8. `released`（已放行）
9. `returned`（已退回）
10. `blocked`（阻塞）
11. `done`（完成）

## 6.2 Work Item 状态流转图

```text
draft
  ↓
clarifying
  ↓（Goal/Boundary/Questions 达标）
plan_ready
  ↓（生成 Plan）
plan_pending_approval
  ├─ 批准 → approved
  └─ 退回 → clarifying / plan_ready

approved
  ↓
executing
  ↓（提交 Artifact + Evidence）
review_pending
  ├─ 放行 → released → done
  ├─ 补充证据 → executing
  └─ 退回重做 → returned → executing / clarifying

任何阶段
  └─ 遇到外部依赖/关键缺失 → blocked
```

---

## 6.3 子状态机 A：Plan 状态机

### 状态
1. `draft`
2. `generated`
3. `pending_approval`
4. `approved`
5. `rejected`
6. `superseded`

### 流转
```text
计划生成 → generated
  ↓
pending_approval
  ├─ 批准 → approved
  ├─ 驳回 → rejected
  └─ 被新计划替代 → superseded
```

### 关键规则
- 没有 `approved` 的 Plan，不允许启动正式执行。
- 一个 Work Item 同时只能有一个 active approved plan。
- 如果 Boundary 或关键 Success Criteria 被修改，原 Plan 应转为 `superseded`。

---

## 6.4 子状态机 B：Artifact 状态机

### 状态
1. `in_progress`
2. `evidence_missing`
3. `submitted`
4. `under_review`
5. `accepted`
6. `returned`
7. `archived`

### 流转
```text
执行产生产物 → in_progress
  ├─ 证据不足 → evidence_missing
  ├─ 证据齐备并提交 → submitted
  ↓
under_review
  ├─ 通过 → accepted
  ├─ 补证据 → evidence_missing
  └─ 退回修改 → returned → in_progress
```

### 关键规则
- Artifact 不应在 `evidence_missing` 状态下直接进入放行。
- `submitted` 不是“已完成”，只是“提交验收”。
- 多轮修改应产生多个 Artifact version，而不是覆盖历史。

---

## 6.5 子状态机 C：Acceptance 状态机

### 状态
1. `not_started`
2. `checklist_ready`
3. `reviewing`
4. `approved`
5. `returned_for_evidence`
6. `returned_for_rework`
7. `waived_with_risk`

### 流转
```text
Artifact 提交 → checklist_ready
  ↓
reviewing
  ├─ 通过 → approved
  ├─ 缺证据 → returned_for_evidence
  ├─ 结果不符合 → returned_for_rework
  └─ 风险可接受但留痕放行 → waived_with_risk
```

### 关键规则
- `approved` 与 `waived_with_risk` 都是可放行状态，但语义不同。
- `waived_with_risk` 必须记录接受了哪些风险、由谁接受。
- 退回需要区分“补证据”和“重做结果”，不能混成同一种失败。

---

# 七、状态机栅栏与关键动作

## 7.1 栅栏 1：进入计划前的清晰度栅栏

### 进入条件
Work Item 只有同时满足以下条件，才能从 `clarifying` 进入 `plan_ready`：
- Goal 已明确
- Boundary 已明确
- 至少有一版 Success Criteria
- 关键 Open Questions 已被解决或明确接受
- 基本上下文已挂接

### 关键动作
- 补充上下文
- 修订 Goal/Boundary
- 标记待确认项是否关闭

### 产品意义
这确保系统不会把“看起来像需求”的内容误当作“可执行任务”。

---

## 7.2 栅栏 2：进入执行前的审批栅栏

### 进入条件
Work Item 只有在以下条件满足后，才能从 `plan_pending_approval` 进入 `approved` / `executing`：
- 已生成 Plan
- 关键依赖与顺序被标注
- 存在明确审批动作
- 没有未处理的高风险越界项

### 关键动作
- 批准
- 退回补计划
- 标记阻塞

### 产品意义
把“先计划”从口号变成系统强约束。

---

## 7.3 栅栏 3：进入放行前的证据栅栏

### 进入条件
Artifact 只有在以下条件满足后，才能进入 `under_review` / `review_pending`：
- 执行摘要已填写
- 有至少一类核心 Evidence（代码 diff、测试结果、文档引用、预览结果等）
- 风险与未覆盖项已显式列出
- 已生成验收清单

### 关键动作
- 补证据
- 提交验收
- 补充风险说明

### 产品意义
这确保“有结果”与“可验收”被系统明确区分。

---

## 7.4 栅栏 4：正式完成前的放行栅栏

### 进入条件
Work Item 只有在以下条件满足后，才能从 `review_pending` 进入 `released` / `done`：
- 验收清单已处理
- 放行动作有记录
- 未通过项已被显式处理
- 如果带风险放行，风险接受记录完整

### 关键动作
- 放行
- 带风险放行
- 退回补证据
- 退回重做

### 产品意义
“完成”不再是主观陈述，而是正式状态变更。

# 八、这些设计如何支撑“先计划、带边界、有证据、可放行”

## 8.1 支撑“先计划”

由以下设计共同支撑：
- 可执行对象页中的 Goal / Boundary / Questions 结构化
- 计划审批页中的 Plan 生成与审批动作
- Work Item 从 `plan_pending_approval` 到 `approved` 的强状态流转

结果是：
- 系统默认要求先明确任务，再开始执行；
- AI 不能越过计划栅栏直接把结果扔给团队；
- 负责人可以在真正投入执行成本前做关键判断。

## 8.2 支撑“带边界”

由以下设计共同支撑：
- Boundary 成为一等对象，而不是注释文本
- 计划审批页显式检查是否越界
- Artifact 页必须说明“本轮未做什么”与“未覆盖项”
- 退回机制允许因为边界失真而回退到 clarifying / planning

结果是：
- 不再默认“能做的都顺手做了”；
- 产物可以清楚说明“做到哪、没做到哪”；
- 团队更容易避免范围漂移与责任不清。

## 8.3 支撑“有证据”

由以下设计共同支撑：
- Evidence 成为独立对象
- Artifact Page 的证据面板是主区域而非附件区
- 进入验收前必须经过证据栅栏
- Acceptance 与 Success Criteria 建立映射

结果是：
- 结果评审从“听汇报”变成“看证据”；
- 负责人不需要在多个系统里拼接依据；
- 团队能逐步建立 evidence-based acceptance 习惯。

## 8.4 支撑“可放行”

由以下设计共同支撑：
- 验收放行页是单独页面
- 放行动作与退回动作都需要正式记录
- `approved`、`waived_with_risk`、`returned_for_evidence`、`returned_for_rework` 被明确区分

结果是：
- 放行成为正式治理动作；
- 责任边界更清楚；
- 历史上每一次“为什么能上线/交付”都可追溯。

# 九、对产品与研发的落地含义

## 9.1 对产品设计的含义
- 页面不是按“功能模块”组织，而是按“闭环阶段”组织。
- 每页都必须能回答：当前状态是什么、还缺什么、下一步是什么。
- Goal / Boundary / Evidence / Acceptance 不能藏在二级抽屉里，它们就是 P0 主舞台。

## 9.2 对后端建模的含义
- 不建议只有一个万能 Task 表；至少要拆出 WorkItem / Plan / Artifact / Acceptance / Evidence。
- 状态机需要支持回退，而不是单向完成。
- 需要版本化 Plan 和 Artifact，避免覆盖历史。

## 9.3 对前端交互的含义
- 优先做单对象穿透式导航，而不是多模块跳来跳去。
- 优先做强摘要、强状态、强下一步动作提示。
- 评论要尽量围绕对象与证据，而不是形成新的上下文孤岛。

## 9.4 对实证验证的含义
P0 原型验证时，最值得优先验证的 3 个页面就是：
1. 可执行对象页
2. 计划审批页
3. 执行结果页 + 验收放行页

因为这三页最能验证 NeoDev 是否真的抓住“先计划、带边界、有证据、可放行”的核心心智。

# 十、最关键的 3 个状态机决策

## 决策 1：没有通过计划审批，不允许进入正式执行
这不是体验细节，而是 NeoDev 与黑箱 AI 工具的根本分水岭。  
它确保 P0 的默认工作方式是“先计划后执行”，而不是“先生成后补解释”。

## 决策 2：Artifact 与 Evidence 必须分开建模，并设置“证据不足”状态
这样才能明确区分：
- 结果是否已经做出；
- 结果是否已经可审。  
这一步直接决定 NeoDev 能否支撑 evidence-based acceptance。

## 决策 3：验收退回必须区分“补证据”与“重做结果”
如果只做一个泛化的“打回”状态，团队会失去对问题性质的判断。  
区分两类退回，才能让系统真正支持：
- 结果本身对，但证据不够；
- 结果本身就不符合目标/边界。  
这对后续效率优化、责任复盘、模型改进都非常关键。

# 十二、一句话收口

NeoDev 的 P0 页面与状态机，不是为了把研发流程“记下来”，而是为了把 **计划、边界、证据、放行** 这四个原本容易靠人脑兜底的关键动作，变成系统强约束与共享对象。
