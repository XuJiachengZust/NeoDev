# 一、文档定位与结论先行

## 1.1 本文档解决什么问题
本文档不再停留在方向草稿层，而是要把 NeoDev P0 的以下内容定成统一基线：

1. **核心对象字典**：Work Item / Plan / Artifact / Acceptance 等对象的字段、必填性、主写入口、主要读取方；
2. **主状态机与子状态机**：明确哪些状态属于容器对象，哪些状态属于阶段子对象；
3. **三道栅栏规则**：清晰度栅栏、审批栅栏、证据栅栏的触发条件、阻断条件、放行条件；
4. **页面-对象-动作映射**：每个页面到底在创建、编辑、提交、审核哪个对象；
5. **后续派工边界**：为 T02 / T03 / 后续开发任务包提供统一口径。

## 1.2 基线原则
NeoDev P0 必须坚持以下五条工程原则：

1. **对象分层，不用万能 Task 混装所有语义。**
2. **先通过清晰度栅栏，再允许生成计划。**
3. **先通过审批栅栏，再允许进入正式执行。**
4. **先通过证据栅栏，再允许进入验收与放行。**
5. **状态变化必须带证据、动作人和回退语义。**

## 1.3 本次定盘结论
本基线将 P0 的一等主对象正式收口为：
- `Work Item`
- `Plan`
- `Artifact`
- `Acceptance`
- 以及作为强约束子对象/从属对象的：`Goal` `Boundary` `Context Reference` `Task` `Evidence` `Risk`

其中：
- **Work Item 是主容器对象与闭环主线承载对象；**
- **Plan / Artifact / Acceptance 是分阶段子对象，不与 Work Item 状态混淆；**
- **Goal / Boundary / Success Criteria 不再被视为散文本，而是 Work Item 的强约束字段；**
- **三道栅栏分别卡住“能否计划 / 能否执行 / 能否验收”。**

# 三、统一对象分层模型

## 3.1 对象分层

### A. 主容器对象
- **Work Item**：一次工作的主对象，贯穿从需求到放行的闭环。

### B. 阶段子对象
- **Plan**：某一版执行计划对象。
- **Artifact**：某一轮执行产物对象。
- **Acceptance**：围绕某个 Artifact 的验收与放行对象。

### C. 强约束字段/从属对象
- **Goal**：要达成什么。
- **Boundary**：明确做什么、不做什么、不可突破什么。
- **Success Criteria**：如何判断可通过。
- **Context Reference**：此工作项引用的文档/任务/代码/设计/讨论等来源。
- **Task**：Plan 下生成的执行单元。
- **Evidence**：支撑 Artifact 可被评审的证据。
- **Risk**：风险、假设、未覆盖项、接受风险记录。

## 3.2 核心关系

```text
Work Item
 ├─ has one Goal set
 ├─ has one Boundary set
 ├─ has many Success Criteria
 ├─ has many Context References
 ├─ has many Risks / Open Questions
 ├─ has zero or one active Plan
 ├─ has many Plan versions
 ├─ has many Artifact versions
 └─ has one or more Acceptance records

Plan
 ├─ belongs to one Work Item
 ├─ generates many Tasks
 └─ is approved / rejected / superseded before execution

Artifact
 ├─ belongs to one Work Item
 ├─ may reference one Plan version
 ├─ has many Evidence items
 ├─ has many Risks / uncovered items
 └─ enters Acceptance flow

Acceptance
 ├─ belongs to one Artifact version
 ├─ maps to Success Criteria
 └─ records release / return / waiver decision
```

## 3.3 对象拆分的强规则

1. **Work Item 不直接等于 Plan，也不直接等于执行结果。**
2. **Plan 是“准备怎么做”，Artifact 是“实际做了什么”，Acceptance 是“是否可以放行”。**
3. **同一个 Work Item 可以有多版 Plan、多轮 Artifact、多次 Acceptance 记录。**
4. **状态判断必须优先看对象自身状态，不允许偷用相邻对象状态。**

# 五、主状态机与子状态机

## 5.1 主状态机：Work Item

### 5.1.1 状态枚举
- `draft`：草稿，刚创建，尚未完成基础结构化。
- `clarifying`：待澄清/待确认，正在补 Goal / Boundary / Questions / Context。
- `plan_ready`：满足计划前清晰度要求，可生成 Plan。
- `plan_pending_approval`：已生成 Plan，等待审批。
- `approved`：计划已批准，可进入正式执行准备。
- `executing`：执行中，正在产生产物或补做。
- `review_pending`：已有待验收 Artifact，等待评审/放行。
- `released`：已放行，可视为业务交付完成。
- `returned`：被退回，需要补证据、修订计划或重做执行。
- `blocked`：因外部依赖、关键缺失或明确阻塞而停住。
- `done`：流程结案态；通常在 `released` 后归档完成。

### 5.1.2 主流转规则

```text
draft
  ↓
clarifying
  ↓（通过清晰度栅栏）
plan_ready
  ↓（生成 Plan）
plan_pending_approval
  ├─ 批准 → approved
  ├─ 退回补计划/补信息 → clarifying 或 plan_ready
  └─ 阻塞 → blocked

approved
  ↓（启动正式执行）
executing
  ↓（提交可审 Artifact）
review_pending
  ├─ 放行 → released → done
  ├─ 补证据 → returned → executing
  ├─ 重做结果 → returned → executing
  ├─ 计划失效/边界变更 → returned → clarifying 或 plan_ready
  └─ 外部阻塞 → blocked
```

### 5.1.3 主状态机关键约束
1. Work Item 不得从 `clarifying` 直接跳到 `executing`。  
2. Work Item 不得在 `plan_pending_approval` 未批准时进入 `executing`。  
3. Work Item 不得在没有待验收 Artifact 的情况下进入 `review_pending`。  
4. Work Item 的 `returned` 是主线回退信号，具体退回原因要由 Plan / Artifact / Acceptance 对象承载。  

---

## 5.2 子状态机：Plan

### 5.2.1 状态枚举
- `draft`
- `generated`
- `pending_approval`
- `approved`
- `rejected`
- `superseded`

### 5.2.2 流转规则
```text
draft → generated → pending_approval
pending_approval
  ├─ 批准 → approved
  ├─ 驳回 → rejected
  └─ 被新计划替代 → superseded

approved
  └─ 若目标/边界关键变化 → superseded
```

### 5.2.3 关键约束
1. `approved` 前不得视为可执行计划。  
2. `rejected` 表示此版计划被否；不是整个 Work Item 作废。  
3. `superseded` 表示计划因新版本出现而失效，不代表该版内容有误。  

---

## 5.3 子状态机：Artifact

### 5.3.1 状态枚举
- `in_progress`
- `evidence_missing`
- `submitted`
- `under_review`
- `accepted`
- `returned`
- `archived`

### 5.3.2 流转规则
```text
in_progress
  ├─ 证据不足 → evidence_missing
  └─ 证据齐备并提交 → submitted

submitted → under_review
under_review
  ├─ 通过 → accepted
  ├─ 缺证据 → returned 或 evidence_missing
  ├─ 结果不符合 → returned
  └─ 新版本产生后旧版归档 → archived
```

### 5.3.3 关键约束
1. `submitted` 只表示提交，不表示通过。  
2. `accepted` 仅代表该 Artifact 通过了验收，不自动等价于 Work Item `done`。  
3. 若评审意见要求补证据但结果本体没问题，优先流转到 `evidence_missing` 语义；若需要重新产出，则流转 `returned`。  

---

## 5.4 子状态机：Acceptance

### 5.4.1 状态枚举
- `not_started`
- `checklist_ready`
- `reviewing`
- `approved`
- `returned_for_evidence`
- `returned_for_rework`
- `waived_with_risk`

### 5.4.2 流转规则
```text
not_started → checklist_ready → reviewing
reviewing
  ├─ 通过 → approved
  ├─ 缺证据 → returned_for_evidence
  ├─ 结果不符合 → returned_for_rework
  └─ 有风险但明确接受 → waived_with_risk
```

### 5.4.3 关键约束
1. `approved` 和 `waived_with_risk` 都可触发 Work Item 放行。  
2. `returned_for_evidence` 必须回到补证据路径，不应默认重开计划。  
3. `returned_for_rework` 默认回到执行路径；若发现计划本身错误，可再回退到 Plan/Work Item。  

---

# 六、三道栅栏规格

## 6.1 栅栏总原则
三道栅栏是 NeoDev P0 的最小强约束，不是提示文案，也不是可忽略提醒。  
每一道栅栏都必须回答四件事：
1. 何时触发检查；
2. 哪些条件不足会阻断；
3. 哪些条件满足可放行；
4. 阻断后回到哪个页面/对象继续补齐。

---

## 6.2 第一栅栏：清晰度栅栏（Clarity Gate）

### 6.2.1 触发时机
当用户在可执行对象页尝试执行以下动作时触发：
- 点击“进入计划”
- 点击“生成 Plan”
- 将 Work Item 从 `clarifying` 推进到 `plan_ready`

### 6.2.2 阻断条件
出现以下任一情况即 block：
1. `goal` 为空或表述过于模糊；
2. `boundary_in` 或 `boundary_out` 缺失；
3. `success_criteria` 为空；
4. 存在关键 `open_questions` 未处理且未被显式接受；
5. `context_refs` 未达到最小要求；
6. 发现高风险但没有记录或处理方式。

### 6.2.3 最小放行条件
同时满足以下条件才 pass：
1. Goal 清楚；
2. 做什么 / 不做什么都清楚；
3. 至少一版 Success Criteria 已存在；
4. Open Questions 要么被关闭，要么被标记为可接受风险；
5. 至少挂接最小上下文：**文档/历史任务/代码范围三类中至少具备其一，且总引用数 ≥ 1；对技术任务建议至少有代码范围或历史任务其一。**

### 6.2.4 放行后结果
- Work Item：`clarifying → plan_ready`
- `clarity_gate_status = pass`

### 6.2.5 阻断后回退路径
- 保持在可执行对象页；
- Work Item 停留 `clarifying`；
- 系统需展示结构化 block 原因，例如：
  - 缺少明确不做范围
  - 缺少成功标准
  - 仍有 2 个关键待确认问题未关闭
  - 未挂接最小必要上下文

---

## 6.3 第二栅栏：审批栅栏（Approval Gate）

### 6.3.1 触发时机
当用户在计划审批页尝试执行以下动作时触发：
- 批准 Plan
- 启动正式执行
- 将 Work Item 从 `plan_pending_approval` 推到 `approved/executing`

### 6.3.2 阻断条件
出现以下任一情况即 block：
1. 不存在已生成的 Plan；
2. Plan 未包含最小任务拆解、依赖关系或执行顺序；
3. Plan 未明确引用 Goal / Boundary / Context；
4. 存在高风险越界项且未被审批意见接纳；
5. 尚未发生明确审批动作；
6. Work Item 因目标/边界变化导致当前 Plan 已失效。

### 6.3.3 最小放行条件
同时满足以下条件才 pass：
1. 已存在当前有效 Plan；
2. Plan 包含任务拆解、顺序、依赖、关键风险；
3. 审批人做出正式批准动作；
4. 没有未处理的高风险越界项；
5. Plan 仍与当前 Goal / Boundary 一致。

### 6.3.4 放行后结果
- Plan：`pending_approval → approved`
- Work Item：`plan_pending_approval → approved`，再由启动执行动作进入 `executing`

### 6.3.5 阻断后回退路径
- 计划页内退回：Plan → `rejected`；Work Item → `clarifying` 或 `plan_ready`
- 若边界变化：旧 Plan → `superseded`；Work Item → `clarifying` 或 `plan_ready`
- 若外部依赖阻断：Work Item → `blocked`

### 6.3.6 审批栅栏核心制度句
**未审批不得进入正式执行。**  
这是 P0 必须写死的系统约束，不可降级为 UI 提示。

---

## 6.4 第三栅栏：证据栅栏（Evidence Gate）

### 6.4.1 触发时机
当用户在执行结果页尝试执行以下动作时触发：
- 提交 Artifact 进入验收
- 从 `executing` 推进到 `review_pending`
- 在验收页开始正式评审

### 6.4.2 阻断条件
出现以下任一情况即 block：
1. 缺少执行摘要；
2. 缺少“做了什么/没做什么”描述；
3. 不存在核心 Evidence；
4. 风险与未覆盖项未显式列出；
5. 尚未生成验收清单；
6. Evidence 与 Success Criteria 无法基本对应。

### 6.4.3 最小放行条件
同时满足以下条件才 pass：
1. Artifact 已形成结构化结果；
2. 至少存在一类核心证据：代码 diff / 文件变更 / 测试结果 / 验证记录 / 文档引用 / 预览链接 之一；
3. 风险和未覆盖项已明确；
4. 验收清单已生成；
5. 结果页足以支持进入正式评审。

### 6.4.4 放行后结果
- Artifact：`in_progress/evidence_missing → submitted → under_review`
- Acceptance：`not_started → checklist_ready → reviewing`
- Work Item：`executing → review_pending`

### 6.4.5 阻断后回退路径
- Artifact：进入 `evidence_missing` 或留在 `in_progress`
- Work Item：留在 `executing`
- 页面停留在执行结果页，提示具体缺失项，例如：
  - 缺测试记录
  - 缺文件变更证据
  - 风险/未覆盖项未填写
  - 验收清单未生成

### 6.4.6 证据栅栏核心制度句
**有结果，不等于可验收；有证据，才允许进入放行判断。**

---

# 七、页面 - 对象 - 动作映射基线

## 7.1 总体映射原则
1. 每个页面必须有主对象，不允许同一字段在多个页面并列主写。  
2. 每个关键动作必须对应对象状态变化。  
3. 页面动作以“创建/编辑/提交/审批/验收/退回”六类为主，避免灰色语义。  

## 7.2 映射表

| 页面 | 主对象 | 次对象 | 主读字段/内容 | 主写字段/动作 | 触发状态变化 |
|---|---|---|---|---|---|
| 任务列表/首页 | Work Item | Plan/Artifact/Acceptance 摘要 | 标题、状态、阻塞、最近更新时间、待处理动作 | 新建 Work Item、筛选、进入详情 | 无直接核心流转，主要导航 |
| 需求输入页 | Work Item | Context Reference（初始） | raw_input、source_type、task_type | 创建 Work Item；写入 raw_input/source_type/task_type/title；挂初始上下文 | 新建后 `draft` |
| 可执行对象页 | Work Item | Goal/Boundary/Success Criteria/Risk/Context Reference | 结构化对象字段、缺失项、清晰度状态 | 编辑 goal/boundary/success_criteria/open_questions/risks/context_refs；提交进入计划 | `draft/clarifying → plan_ready` |
| 计划审批页 | Plan | Work Item/Task/Risk | 计划摘要、拆解、依赖、计划依据、审批意见 | 生成 Plan；编辑 task_breakdown/dependencies/execution_order；批准/退回/阻塞 | Work Item `plan_ready → plan_pending_approval → approved/blocked/clarifying`；Plan `generated → pending_approval → approved/rejected/superseded` |
| 执行结果页 | Artifact | Evidence/Risk/Work Item | 执行摘要、完成/未完成、证据面板、风险、评论 | 创建/编辑 Artifact；补充 Evidence；提交验收 | Work Item `approved/executing → review_pending`；Artifact `in_progress/evidence_missing → submitted/under_review` |
| 验收放行页 | Acceptance | Artifact/Work Item/Evidence | 验收清单、证据映射、评审意见、历史记录 | 审核清单；批准/补证据/重做/带风险放行 | Acceptance `reviewing → approved/returned_for_evidence/returned_for_rework/waived_with_risk`；Work Item `review_pending → released/returned` |

## 7.3 页面主写边界

### 7.3.1 需求输入页主写什么
- 只主写原始输入与初始元信息；
- 不应在此页承载完整 Goal/Boundary 深度编辑。

### 7.3.2 可执行对象页主写什么
- 主写 Work Item 的结构化定义；
- 是 Goal / Boundary / Success Criteria / Open Questions / Context 的主编辑入口。

### 7.3.3 计划审批页主写什么
- 主写 Plan 对象及审批动作；
- 不应越俎代庖修改原始 raw_input。

### 7.3.4 执行结果页主写什么
- 主写 Artifact / Evidence / 本轮风险；
- 不直接替代验收页做放行决策。

### 7.3.5 验收放行页主写什么
- 主写 Acceptance 决策与退回原因；
- 不直接修改执行结果正文，只能要求补证据或重做。

# 八、回退与异常处理规则

## 8.1 回退必须分类，不许笼统“打回”
P0 中至少要区分四类回退：
1. **清晰度不足回退**：回到可执行对象页补 Goal / Boundary / Context；
2. **计划审批回退**：回到计划页或对象页补计划依据/边界；
3. **证据不足回退**：回到执行结果页补 Evidence；
4. **结果不符合回退**：回到执行路径重做 Artifact，必要时触发计划重开。

## 8.2 blocked 的使用规则
`blocked` 只用于以下情况：
- 外部依赖未满足；
- 关键前提长期缺失；
- 需要老大/负责人额外决策；
- 明确存在无法继续推进的外部障碍。

`blocked` 不应用来掩盖“其实只是字段没补全”的情况。

## 8.3 superseded 的使用规则
`superseded` 只用于 Plan 或 Artifact 的版本替代语义：
- Goal/Boundary 变化导致旧计划失效；
- 新一轮更完整的 Artifact 产生，旧版本归档。

## 8.4 released 与 done 的关系
- `released`：表示已经完成正式放行；
- `done`：表示该 Work Item 生命周期已结案/归档。

P0 可允许两种实现方式：
1. 放行后人工/系统再进入 `done`；
2. 放行即视为完成，再异步归档。

但无论如何，**不能跳过 released 直接 done**，否则“放行记录”会失去主路径意义。

# 十、最关键的 3 个定盘决策

## 决策 1：Work Item 是主容器，Plan / Artifact / Acceptance 必须拆开，不允许退化回万能 Task
理由：
- 不拆开，状态语义一定混乱；
- 不拆开，计划、结果、验收就会重新混成一页；
- 不拆开，后续派工与验收口径无法稳定。

## 决策 2：三道栅栏写成系统前置条件，不写成提示文案
理由：
- 清晰度栅栏决定“能否计划”；
- 审批栅栏决定“能否执行”；
- 证据栅栏决定“能否验收”；
- 只要任何一道变成弱提醒，NeoDev 就会重新退化成黑箱生成器。

## 决策 3：验收退回必须区分“补证据”和“重做结果”，Plan 替换必须区分“rejected”和“superseded”
理由：
- 问题性质不同，回退路径就不同；
- 如果混成一个退回态，后续子智能体、产品、研发都无法稳定判断下一步动作；
- 这也是后续度量返工原因、模型问题、流程问题的基础。
