# 一、PRD 结论先行

## 1.1 P0 一句话定义
NeoDev P0 不做“大而全 AI 研发平台”，只打透一条最小但完整、可被团队采纳的人机协作研发闭环：

**模糊需求输入 → 结构化对象包 → 上下文聚合 → 计划审批 → 执行结果对象化 → 证据化评审 → 验收放行**

## 1.2 为什么现在就该这样收敛
当前 AI 已进入研发，但多数团队仍靠“文档 + 聊天 + 人脑转述 + 负责人兜底”推进，导致：
- 需求理解不一致
- 上下文反复丢失
- AI 虽能生成，但不能被正式纳入团队流程
- 结果难评审、难放行、难复用

NeoDev 的机会，不在于再做一个更强生成器，而在于把 **需求、上下文、执行、证据、验收** 连成一条可信链路。

## 1.3 本 PRD 的核心判断
P0 应优先服务一个最有痛感、也最有 adoption 可能的用户群：
**Tech Lead / 工程经理 / 高 AI 使用密度的资深工程师所在的小中型高迭代团队。**

因为他们同时对：
- 目标是否清晰
- 执行是否跑偏
- AI 输出是否可信
- 团队是否敢放行

承担真实责任。

# 三、产品目标与非目标

## 3.1 产品目标
P0 目标不是证明 NeoDev 能做很多 AI 功能，而是证明一件事：

> **NeoDev 可以让团队把 AI 纳入正式研发闭环，并让关键负责人愿意基于系统里的共享对象、证据与验收记录做放行决策。**

具体分解为 4 个目标：
1. 把模糊需求快速转成可执行对象，而不是停留在聊天与摘要层。
2. 把分散上下文聚合成同一任务对象，减少转述和反复解释。
3. 强制“先计划、后执行”，降低任务跑偏和黑箱推进。
4. 把执行结果变成可评审、可证据化、可放行的结果对象。

## 3.2 非目标
P0 明确不做以下内容：
1. 不做大而全项目管理/Jira 替代。
2. 不做通用 IDE/编码助手替代。
3. 不做复杂组织治理层（多级审批、细颗粒权限、跨部门流程编排）。
4. 不先做经验沉淀自动化、组织知识飞轮的完整体系。
5. 不优先适配大型企业复杂流程与长采购链场景。
6. 不以模型能力强弱作为核心卖点。

# 四、目标用户

## 4.1 核心目标用户

### 用户类型 A：Tech Lead / 工程经理
特征：
- 对目标、节奏、质量、风险负责
- 最怕需求不清、返工、AI 结果不可控
- 有采用新工作流的推动权

核心诉求：
- 尽快看清“要做什么、不做什么、如何验收”
- 在执行前发现歧义和风险
- 在结果阶段基于证据做放行，而不是凭感觉背锅

### 用户类型 B：高 AI 使用密度的资深工程师 / 全栈工程师 / 产品工程师
特征：
- 已经深度使用 AI 参与编码、分析、文档
- 对上下文丢失、多工具切换非常敏感
- 愿意尝试新的人机协作范式

核心诉求：
- 少做重复转述与二次整理
- 让 AI 的输出更容易被团队接受
- 让自己的工作结果更容易被快速 review 和通过

### 用户类型 C：小到中型高迭代产品团队
特征：
- 组织还未完全僵化
- 协作频繁、节奏快、返工成本高
- 对“first win”敏感，适合新方法快速进入正式流程

核心诉求：
- 用尽量小的流程变化换来更强的协同质量
- 在不推翻现有工具栈的情况下补上断裂带

## 4.2 不优先用户
- 只想自动写代码的个人用户
- 没有明确验收纪律的松散团队
- 大型复杂企业的首阶段切入

# 五、核心问题定义

P0 要解决的不是“AI 不够聪明”，而是以下 5 个结构性问题：

## 5.1 需求无法直接进入执行
现状：需求常以 PRD、聊天、会议结论存在，信息很多，但没有被转成明确的目标、边界、依赖和验收条件。

后果：
- 每个人都要重新理解一遍
- AI 只能做摘要，无法稳定形成可执行对象
- 执行开始得很快，但方向常常并不一致

## 5.2 上下文依赖人脑转述
现状：相关文档、历史任务、代码模块、设计稿、聊天记录分散在多个地方。

后果：
- 新参与者理解成本高
- 负责人被迫承担上下文搬运工角色
- 类似问题重复讨论，组织没有复利

## 5.3 AI 先执行、后解释
现状：很多 AI 工具直接产出答案或代码，但没有显式计划、边界说明和待确认项。

后果：
- 团队不敢信
- 容易“看起来很快，实际上返工更大”
- 真正的风险在执行后才暴露

## 5.4 结果不可审查、不可放行
现状：AI 常只说“完成了”，但团队真正需要知道：改了什么、依据是什么、测了没有、还有什么没覆盖。

后果：
- review 成本高
- 放行责任模糊
- 团队只能回到口头同步和人工兜底

## 5.5 结果没有形成组织资产
现状：任务做完后，计划依据、评审意见、放行原因、未覆盖项常常散失。

后果：
- 类似任务无法复用
- 团队很难建立新的默认工作方式

# 六、P0 产品范围

## 6.1 P0 核心闭环范围
P0 只覆盖以下四段：
1. **需求结构化**
2. **上下文聚合**
3. **计划生成与审批**
4. **结果评审与证据化验收**

## 6.2 P0 必须做的能力

### A. 需求结构化
- 原始需求输入
- Goal 自动提取
- Boundary 自动提取
- Success Criteria / 验收标准草案
- Risks / 假设 / 未知项提取
- 待确认问题列表
- 一键生成“可执行对象包”

### B. 上下文聚合
- 文档关联
- 历史任务关联
- 代码模块关联
- 上下文摘要卡片
- 引用来源展示

### C. 计划生成与执行管控
- 任务拆解生成
- 依赖与执行顺序标注
- 执行前待确认栅栏
- 计划审批节点
- 对象状态流转
- 执行计划摘要页

### D. 结果评审与证据化验收
- 结构化结果页
- 执行内容摘要
- 文档证据展示
- 代码 diff / 文件变更展示
- 测试结果 / 验证记录展示
- 风险面板
- 未覆盖项列表
- 围绕结果页的评论线程
- 验收清单
- 放行 / 退回记录

## 6.3 P0+ 可紧随其后但不阻塞首发的能力
- 结构化结果人工修订
- 对象状态提示更细化
- 设计稿 / 讨论记录关联
- 缺失上下文提醒
- 优先级与负责人建议
- 审批意见记录
- 预览链接
- 结果 diff
- 退回原因结构化记录

# 七、核心用户旅程

## 7.1 旅程总览

### 阶段 1：输入需求
用户将 PRD、需求描述、会议纪要或聊天摘要输入系统。

系统目标：把“讨论材料”变成“待结构化对象”。

### 阶段 2：形成可执行对象包
系统抽取并生成：
- Goal
- Boundary
- Success Criteria
- Risks
- Open Questions
- Context Summary

用户动作：修订关键字段，确认哪些问题必须先澄清。

成功标志：需求不再只是文本，而成为一个可进入计划阶段的对象。

### 阶段 3：关联上下文
用户补充或系统关联：
- 相关文档
- 历史任务
- 代码模块
- 必要设计稿/讨论记录

系统目标：形成共享上下文，避免后续转述。

成功标志：任何进入此任务的人，都能在一屏中理解背景与依据。

### 阶段 4：生成计划并审批
系统生成：
- 任务拆解
- 依赖关系
- 执行顺序
- 验收建议
- 待确认栅栏

负责人动作：
- 审核计划
- 明确不可越界项
- 批准进入执行

成功标志：计划获得负责人确认，且关键待确认项已被显式处理。

### 阶段 5：执行结果对象化
AI 或人完成执行后，系统生成结果页，结构化展示：
- 做了什么
- 没做什么
- 对应哪些需求与计划
- 变更证据是什么
- 测试与验证情况如何
- 风险与未覆盖项是什么

成功标志：结果不是一句“完成了”，而是一个可供共享评审的 Artifact。

### 阶段 6：评审与放行
评审人与负责人围绕结果页评论、查看证据、逐条验收，并进行：
- 放行
- 退回重做
- 要求补充证据

成功标志：形成明确的责任记录与放行依据。

# 八、关键对象模型

## 8.1 需求对象（Requirement Intake）
字段建议：
- 标题
- 原始输入内容
- 来源类型（PRD/会议/聊天/其他）
- 创建人
- 当前状态

意义：所有任务的起点对象，承载“模糊输入”。

## 8.2 可执行对象包（Executable Brief）
字段建议：
- Goal
- Boundary
- Success Criteria
- Risks
- Open Questions
- 假设与依赖
- 引用来源

意义：NeoDev 的第一个关键产品对象，代表从“需求材料”升级为“可规划对象”。

## 8.3 上下文包（Context Bundle）
字段建议：
- 关联文档
- 历史任务
- 代码模块
- 设计稿 / 讨论记录
- 摘要视图
- 引用链路

意义：让协作围绕共享上下文，而不是围绕转述。

## 8.4 计划对象（Execution Plan）
字段建议：
- 任务拆解
- 子任务列表
- 依赖关系
- 优先级
- 审批状态
- 审批意见
- 待确认栅栏状态

意义：落实“先计划、后执行”的核心规则。

## 8.5 结果对象（Artifact / Result Page）
字段建议：
- 执行摘要
- 实际变更内容
- 文档证据
- 代码 diff
- 测试记录
- 风险与未覆盖项
- 评论线程
- 验收清单
- 放行记录

意义：NeoDev 的第二个关键产品对象，承载“可审查、可放行的结果”。

## 8.6 验收记录（Acceptance Record）
字段建议：
- 验收人
- 验收时间
- 验收动作（放行/退回/待补充）
- 验收依据
- 备注

意义：将责任节点正式产品化。

# 九、关键页面定义

## 9.1 页面 1：需求输入与结构化页
目标：把原始需求快速转成可执行对象包。

页面模块：
- 原始输入区
- 自动提取结果区（Goal / Boundary / Success Criteria / Risks / Open Questions）
- 人工修订区
- 一键生成对象包按钮

关键要求：
- 不能只给摘要，必须输出结构化字段
- 模糊项必须显式暴露，不允许系统自动黑箱补平

## 9.2 页面 2：任务上下文总览页
目标：让所有参与者一屏理解任务背景。

页面模块：
- 任务基础信息
- 关联文档
- 历史任务
- 代码模块
- 上下文摘要
- 引用来源视图

关键要求：
- 必须让新进入者在短时间内建立上下文
- 必须看到依据来自哪里

## 9.3 页面 3：计划审批页
目标：把“计划是否可执行”变成正式决策节点。

页面模块：
- 计划摘要
- 任务拆解
- 依赖与顺序
- 待确认项栅栏
- 审批意见
- 批准 / 驳回动作

关键要求：
- 未解决关键待确认项时，不允许进入执行态
- 审批不是备注，而是主流程节点

## 9.4 页面 4：结果页 / Artifact Page
目标：把执行结果变成统一评审对象。

页面模块：
- 计划摘要与目标回看
- 本轮做了什么 / 没做什么
- 证据面板（文档、diff、测试、预览）
- 风险与未覆盖项
- 评论线程
- 验收清单与放行记录

关键要求：
- 结果必须对象化，而不是散落在聊天和截图
- 证据与风险必须和结果同页出现

## 9.5 页面 5：验收与放行面板
目标：支持负责人基于证据完成正式放行。

页面模块：
- Success Criteria 对应 checklist
- 评论与问题汇总
- 放行 / 退回 / 补充信息动作
- 历史记录

关键要求：
- 让“谁基于什么批准了什么”可回看
- 让退回原因与补充要求可追踪

# 十、核心交互规则

## 10.1 先计划后执行
任何对象在关键待确认项未处理、计划未审批前，不应进入正式执行态。

## 10.2 先显式边界再谈产出
所有 AI 输出必须挂在 Goal / Boundary / Success Criteria 之下，不能脱离边界直接生成“答案”。

## 10.3 风险与未覆盖项必须默认可见
系统不能只展示“成功部分”，必须同步展示：
- 未覆盖范围
- 风险项
- 待人工确认项

## 10.4 引用必须可回溯
计划、结果、评论中的关键判断应可追溯到来源文档、历史任务或代码范围。

## 10.5 验收是主路径，不是附件
验收记录、批注、放行动作必须产品化，而不是依赖外部聊天补充。

# 十一、成功指标

## 11.1 P0 核心产品指标

### 指标 A：结构化转化率
定义：输入原始需求后，成功生成并被用户保留/进入后续计划阶段的“可执行对象包”比例。

建议目标：> 60%

### 指标 B：计划审批通过率
定义：进入计划页的任务中，能在 1 次或少量修订后进入批准执行状态的比例。

建议目标：> 50%

### 指标 C：结果页放行率
定义：有结构化结果页的任务中，被负责人正式放行的比例。

建议目标：> 40%

### 指标 D：证据完整率
定义：进入验收阶段的结果页中，同时具备目标引用、变更证据、测试/验证记录、风险说明的比例。

建议目标：> 80%

### 指标 E：主观信任提升
定义：Demo/试用后，用户对“AI 输出可进入正式团队流程”的认同度提升。

建议目标：访谈中 > 70% 的受访者明确认可

## 11.2 业务验证指标
- 用户是否明确认同“链路断裂、靠转述推进”是现有核心问题
- 用户更愿意把哪个场景作为 first win：需求→计划，还是结果→验收
- 谁会成为团队 adoption 推动者，谁会成为阻力来源

# 十二、验收标准

## 12.1 P0 版本验收标准

### A. 需求结构化验收
1. 用户可输入一份原始需求文本并生成结构化对象包。
2. 输出至少包含 Goal、Boundary、Success Criteria、Risks、Open Questions。
3. 用户可修订关键字段并保存。
4. 系统能显式标记关键信息缺失或待确认项。

### B. 上下文聚合验收
1. 可挂接文档、历史任务、代码模块三类核心上下文。
2. 页面能展示上下文摘要与引用来源。
3. 新参与者可在同一任务页理解当前背景，不需先去多个外部位置寻找信息。

### C. 计划审批验收
1. 系统可基于对象包生成任务拆解、依赖与执行顺序。
2. 存在关键待确认项时，不能直接进入执行态。
3. 负责人可完成批准/驳回动作，并保留审批记录。
4. 对象状态至少覆盖：草稿、待确认、待审批、已批准、执行中。

### D. 结果评审验收
1. 执行结果可生成结构化结果页。
2. 结果页至少展示：计划摘要、执行内容、文档证据、代码 diff/文件变更、测试/验证记录、风险与未覆盖项。
3. 评审人可围绕结果页评论。
4. 验收清单可逐项确认。
5. 负责人可执行放行 / 退回 / 要求补证据动作，并形成记录。

### E. Demo 验收
1. 能完整演示“模糊需求 → 可执行计划”链路。
2. 能完整演示“执行结果 → 证据化验收”链路。
3. 演示对象可在 15-25 分钟内看懂 NeoDev 不是另一种 AI 聊天工具，而是闭环层。

# 十三、主要风险与对应策略

## 13.1 风险一：流程过重，用户感到负担增加
策略：
- P0 只做最短闭环，不做复杂治理
- 尽量自动生成对象包，降低输入成本
- 让每一步都产生可见收益，而不是形式化步骤

## 13.2 风险二：用户仍把产品理解成“总结工具”
策略：
- 强调“对象包”“计划审批”“结果页”“放行记录”四个关键对象
- Demo 不先讲 AI 能力，先讲旧流程断裂和团队不敢信的问题

## 13.3 风险三：证据接入不完整，结果页空心化
策略：
- 首批优先打通最关键证据：文档引用、代码变更、测试记录
- 暂不追求全量自动化，允许部分人工补充

## 13.4 风险四：负责人不愿承担额外审批动作
策略：
- 审批动作设计成“降低背锅风险”的能力，而不是“增加流程负担”的能力
- 让放行动作直接绑定证据和责任记录

---

# 十四、P0 最关键的 3 个设计决策

## 决策 1：P0 先做“需求→计划”和“结果→验收”两端，不做中间无限扩展的执行平台
理由：
- 这是最能体现 NeoDev 闭环价值的两端
- 也是最容易 demo、最容易建立老板和用户心智的位置
- 中间执行层可以先借助现有工具与人工协作，不必一次做全

## 决策 2：产品核心对象不是“聊天消息”，而是“可执行对象包”和“结果对象页”
理由：
- 聊天消息无法承载团队协作、引用、评审、责任和放行
- 真正能进入正式流程的，是结构化对象，而不是对话记录

## 决策 3：必须把“待确认项栅栏 + 审批节点 + 风险/未覆盖项显式化”做成主路径
理由：
- 这是 NeoDev 与黑箱 AI 工具最本质的差异
- 也是负责人愿不愿意让 AI 进入正式流程的关键前提
- 若缺少这三项，产品会重新退化为“更聪明但仍不可控的生成器”

# 十六、最终结论
NeoDev P0 的成败，不取决于它是否比别的 AI 更能生成，而取决于它是否能让团队形成一个新的默认认知：

> **AI 参与研发时，正确方式不是让它直接给答案，而是让它在共享上下文、明确边界、计划先行、证据充分、验收可追踪的闭环里工作。**

如果 P0 能把这条链路跑通，NeoDev 就不再是一个附加工具，而会开始占据团队默认工作方式中的关键层。
